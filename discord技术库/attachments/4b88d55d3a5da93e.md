# MMD 状态栏规范发展史

> 本文档梳理了 MMD（魅魔岛/sexyai.top）平台上状态栏技术从蛮荒时代到工业化交付的完整演变历程。
> 这不是一个「1.0→2.0→3.0」的线性升级故事，而是多位作者从不同角度攻击同一座堡垒，
> 逐步积累出一个工具箱的过程。

---

## 序章：蛮荒时代——AI 手写 HTML 的状态栏

在最早期的 MMD 角色卡中，状态栏是这样生成的：

> 模型在每一轮回复末尾，用自然语言手写完整的 HTML 状态栏代码。

这带来了几个致命问题：

1. **Token 浪费**：每轮都要输出完整 HTML，长期不变的信息重复输出
2. **格式崩溃**：模型偶尔漏写闭合标签 → 整个界面崩塌为乱码
3. **平台拦截**：HTML 字符串经过 markdown 管线时被补空 `<p>`、加斜体、注入 font 标签
4. **数值算错**：AI 需要反复读取上文重新计算增减，多轮后必出误差
5. **记忆衰退**：长期不出现的信息逐渐脱离模型的注意力窗口

正是在这样的背景下，社区开始探索「让 AI 少写一点、让代码多做一些」的方向。

## 第一章：柑硕——数据与视图分离的奠基人

**代表作品**：《抓取式状态栏制作规范》

### 核心贡献

柑硕提出了两个后来被所有方案无条件继承的根本原则：

#### 1. 数据与视图分离

不在状态栏里让 AI 手写 HTML。AI 只输出**精简的数据标签**，前端 JS 负责解析并渲染到预制的 HTML 骨架上。

```
AI 输出的不再是：
  【生命值】78/100  【魔力值】45/60  【金钱】5000金币

而是：
  zy="hp:78/100,mp:45/60"  mn="5000"
```

前端通过 `data-f` 标记插槽，JS 自动填充：

```html
<span data-f="mn">--</span>    →  被 JS 自动替换为 "5000"
```

#### 2. 向上继承机制

继承思路的源头来自**心月狐**——他在整体替换法中率先注入了回溯 JS。柑硕将其融入键值法体系：当前消息没有提供的字段，JS 自动向上遍历历史消息，查找最近一次有效值。

```javascript
// 当前消息只更新了 hp，其他字段自动继承
// 第 N-3 条：nm="勇者" mn="1000" zy="hp:100/100,mp:60/60"
// 第 N 条：  zy="hp:80/100"                      ← 只输出变化的！
// 结果：    nm="勇者" mn="1000" zy="hp:80/100,mp:60/60"  ← nm/mn/mp 都继承
```

### 设计细节

| 设计 | 格式 | 说明 |
|------|------|------|
| 资源条 | `zy="hp:78/100,mp:45/60"` | `名称:当前/最大`，逗号分隔 |
| 键值列表 | `bag="剑|1,盾|1,药水|5"` | `物品名|数量`，逗号分隔 |
| 多值列表 | `sk="火球术|10|远程攻击"` | `名称|消耗|描述` |
| 数据分类 | `data-env` / `data-st` / `data-opt` | 环境/状态/选项，各自独立 |
| 触发机制 | `<img onerror="parseStatus(...)">` | 利用图片加载失败触发 JS |
| 颜色系统 | 资源条按索引循环取色 | `COLORS[index % 4]` |

### 历史地位

**柑硕没有被超越。** 他提出的「数据与视图分离」和「继承机制」是这座大厦的地基。如果一个角色卡只有 5 个字段要显示，柑硕方案至今仍然是最佳选择——代码最短、最易理解、零依赖。

后人的所有方案都在柑硕的地基上盖楼，不是推倒重来。

## 第二章：澄清——KV-Robust V2.0，键值法的工程化落地

**代表作品**：《KV-Robust V2.0 技术规范》、《七大核心准则》

### 核心贡献

如果说柑硕解决了「数据格式」问题，澄清的 KV-Robust 解决的则是「代码怎么在这种鬼环境里跑起来」的问题。

#### MMD 平台的真实限制（KV-Robust 时期实测）

| 限制级别 | 限制内容 | 后果 |
|----------|----------|------|
| 零级 | 禁止 `<script>` 标签 | 所有正常 JS 完全失效 |
| 一级 | `onerror`/`onclick` 中 JS 多行 → 被截断 | 代码从第一个换行处断开 |
| 二级 | HTML 中 `<` `>` `&` 等符号被审查 | 比较运算符 `<` 被吃掉 |
| 三级 | 重复 `id` 导致第二次使用失效 | 多条消息渲染在同一页面 |
| 四级 | `onclick` 复杂代码被「净化」或实体化 | 元素直接消失或变成纯文本 |

#### KV-Robust 的应对方案

1. **onerror 点火器**：利用 `<img src="x" onerror="...">` 绕过 `<script>` 禁令 —— 图片加载失败触发 JS
2. **单行压缩**：所有 JS 压缩为严格一行，避免多行截断
3. **KV 键值对结构**：`ts::xxx;;name::张三;;points::200;;` —— 分隔符 `::` 和 `;;`
4. **数据块标记**：`DGS_KV_PANEL_V2_START▶...◀END` —— 正则精准捕获
5. **安全替代写法**：`i != length` 替代 `i < length`，避免 `<` 被转义

### 工程架构

```
AI 输出 KV 数据块
    ↓
正则捕获 → 替换为 HTML 模板（隐藏 <p> 标签存原始数据）
    ↓
<img onerror> 点火 → JS 读取隐藏 <p> 的 textContent
    ↓
运行时解析 KV → 更新对应 DOM 元素的 textContent
```

### 历史地位

**KV-Robust 踩出来的路，后来所有人都走。** onerror 点火器、单行压缩、KV 数据结构——这套绕过技术在影渲法、雷达法中仍在沿用。没有澄清在雷区里一步一步踩出的安全路径，后面所有人的 JS 都跑不起来。

## 第三章：黑洞猫——混合态雷达法，长线智商保卫战

**代表作品**：《一种基于特征嗅探与响应式动态DOM的混合态雷达式状态栏设计规范及示例》（改五版）

### 核心贡献

如果说澄清的 KV-Robust 解决的是「能不能跑」，雷达法解决的则是「跑 200 轮之后模型会不会变傻」。

#### 五级分类理论

雷达法将所有状态栏数据按对模型推理的影响权重与生命周期，分为五级：

| 级别 | 定义 | 例子 | 处理方式 |
|------|------|------|----------|
| **第一类** 全局锚点 | 维持世界观核心逻辑，每轮强制存在 | 主角名、主线目标、纪元背景 | 固态底座：模型每轮输出 + 引擎历史兜底 |
| **第二类** 高频变量 | 每轮大概率变化，驱动角色扮演 | 时间地点、生命值、好感度 | 固态底座：同第一类 |
| **第三类** 后台暗流 | 仅模型可见的隐藏推理线索 | 真实好感度、暗骰结果、杀意阈值 | 折叠隐藏或不渲染到界面 |
| **第四类** 场景快照 | 高刺激特写，**残留会污染长期上下文** | 战损评估、极端感官状态、特殊体液 | 液态快照：情境绑定，**绝不兜底**，离开即销毁 |
| **第五类** 低频冗余 | 真实感补充，极少变动 | 排班表、身高体重、装备说明 | 按需输出，兜底填充 |

#### 第四类数据的洞察——全篇最关键的发现

第四类数据（高刺激感官词汇）如果在历史记录中残留，大语言模型的注意力机制会被这些高权重词汇持续捕获。这意味着：

> 一场 50 轮前的激烈战斗，其「左臂骨折」「大量出血」等词汇残留在上下文中，
> 会导致模型在 50 轮后的日常对话中仍然推演出过度的暴力倾向。

这不是模型「变傻」了，是它的注意力被历史中的高刺激锚点持续拉扯。雷达法的「液态快照无兜底代谢」——模型停止输出该键名后，UI 模块即被从界面上抹除——是直接切断了这个污染链。

**至今没有任何方案真正超越这个洞察。** 影渲法的双轨代谢就是从雷达法直接搬过来的。

#### 其他核心技术

| 技术 | 解决的问题 |
|------|-----------|
| **模糊特征嗅探** | 模型自由发散新键名（如「火焰长剑」），引擎按关键字自动路由到装备区——不要求模型记得精确键名 |
| **内存级动态 DOM 装配** | 不修改页面现有节点，在独立内存中用 `createElement` 拼完再一次性挂载——免疫平台排版引擎篡改 |
| **悬浮气泡交叉绑定** | 装备名「紫木法杖」与释义「每次攻击造成额外奥术伤害」自动匹配绑定——鼠标悬停即显示 |
| **响应式防挤压** | 媒体查询监听视口：宽屏双列网格，窄屏（<800px）自动折叠为单列 |
| **虚拟DOM劫持对抗** | 平台重绘时会抹除注入的外部节点——引擎用短程探针在2.5秒内自检并原地重建，5次后自毁释放资源 |
| **作用域逃逸防御** | 编辑预览框内引擎可能扫描到全页所有历史数据——加层级阈值硬性收缩 |

### 历史地位

**雷达法的五级分类和双轨代谢是理论层面至今未被超越的贡献。** 它把状态栏从「怎么显示」升级到了「怎么保护模型的长线智商」。后人在这个框架上做工程优化，但没有推翻底层理论。

## 第四章：澄清——KVV4.0 融合规范

**代表作品**：《澄清融合技术规范 + KVV4.0》

### 核心贡献

澄清是键值法的首创者，也是 KV-Robust 的作者。在 KV-Robust 之后，他继续推进键值法的工程化整合，把柑硕的抓取式与 onerror 引擎系统地融合在一起：

- 正式引入了 `<status>` 标记触发系统，统一了键值法的正则匹配入口
- 继承了柑硕的 `data-env`/`data-st`/`data-opt` 数据分类和向上继承机制
- 使用分段式正则规则（3条规则协作：容器+CSS → HTML结构 → JS解析器）

### 附加贡献

| 贡献 | 说明 |
|------|------|
| ES5 严格要求 | 禁止 `let`/`const`/箭头函数/`innerHTML`/`cssText`——统一用纯 DOM API |
| 零级红线发现 | img 标签必须在容器闭合 `</div>` 之前——否则 `closest()` 返回 null |
| Token 节省数据 | 首条 ~40%、后续仅更新 HP ~90%、10轮累计 ~84% |

### 历史地位

澄清把状态栏从「手工作坊」推向了「半工业化」。他的分段式规则模板让后续方案可以复用一套稳定的结构框架。醉猫的链式规则、锐的五类文件架构，都是在澄清的「分段」思想上发展的。

## 第五章：锐（AGENT.md）——唯一用架构师视角思考的人

**代表作品**：《AGENT.md》

### 核心贡献

锐是所有人中唯一不关心具体数据格式的人。他关心的是**系统层面的工程问题**。

#### 五类文件架构

不再把代码写在一个大函数里。固定拆成五类独立文件：

1. **界面文件**：长期存在的 DOM 结构，只负责显示
2. **CSS 文件**：样式，不负责数据逻辑
3. **初始化代码文件**：页面打开时运行一次，完成后自删触发节点
4. **回复代码文件**：每条回复触发时运行
5. **中间态正则列表**：只负责「正则式 + 替换内容」，不混入运行逻辑

#### 六步执行链

每次回复代码按固定流程运行（可选步骤可省略）：

```
Stage 1: Self Capture           → var self = this（固定引用）
Stage 2: 初始化依赖协商段       → waitReady() 等待全局初始化完成（可选）
Stage 3: 当前回复自处理段       → 处理当前回复同级的中间态数据（可选）
Stage 4: 最新回复仲裁段         → 判断当前回复是否是最新一条（可选）
Stage 5: 最新回复处理段         → 仅最新回复执行全局单例视图更新（可选）
Stage 6: 结束自删段             → 执行完毕移除触发节点
```

#### 最新仲裁机制——解决了一个隐蔽但致命的问题

页面打开时，历史回复对应的多个回复 img 会**同时加载**。这些 img 的加载顺序不保证与回复时间顺序一致。如果不做仲裁：

> 第 3 条的 img 晚于第 10 条触发 → 旧数据覆盖新数据 → 面板错乱

锐的仲裁规则：基于 `.content.left` 的 DOM 顺序（`replies[replies.length - 2]`），不基于图片加载顺序。直到影渲法，per-message 渲染仍在依赖这个思路。

#### 全局单例 vs 回复级——视图分类

| 类型 | 定义 | 例子 |
|------|------|------|
| 全局单例视图 | 页面级唯一，跨回复复用 | 地图、侧边栏、弹窗、总控浮层 |
| 回复级重复视图 | 每条回复独立实例 | 状态栏块、选项块、日志块 |

两类可并存，但职责不能交叉。这个分类后来直接进入了影渲法的设计。

### 历史地位

锐的贡献是**元层面的**——它们不绑定任何具体渲染技术。六步执行链和最新仲裁，用 Shadow DOM 要做，用 light DOM 也要做。锐没有被超越，他的框架在后来的所有复杂方案中都在被默默遵循。

## 第六章：醉猫——集成测试总监

**代表作品**：《醉猫融合整理技术规范》（v7）→《醉猫融合技术规范终极版》（v8，也称影渲法 1.0）

### 核心贡献

醉猫的 11 万字规范本质上是一份**大规模集成测试报告**。他把所有人的方案放在一起跑，记录了哪些能共存、哪些冲突、「文档说不行但实测能用」的所有例外。

#### v7 → v8 的关键实测发现

| 发现 | 之前的认知 | 醉猫实测 |
|------|-----------|----------|
| replaceString 字符上限 | 10000 | **20000**（含 &继续N& 标记） |
| ES6 在 onerror 中 | 绝对禁止 | **const/let/箭头函数/模板字符串均可使用**（⚠️标记） |
| `\r` 字符 | 未知 | **零级致命**——eval 静默失败，所有渲染不触发 |
| `className` 拼接 | 随便写 | 三元运算符拼接空格在压缩后**被吃掉**，必须完整赋值 |
| `<script>` 标签 | 完全禁止 | 允许三种非执行 type：`application/json`、`text/plain`、`text/json` |
| data-s / script plain | 未知 | **可存多行 JS 绕过 onerror 单行限制** |

#### 工程化创新

| 技术 | 说明 |
|------|------|
| **链式规则** | `&继续N&` 或 `<!-- S_N -->` 标记拼接多条正则，突破单条 20000 字符限制 |
| **美化与功能分离** | 超 20000 字符时拆为规则A（CSS+HTML骨架）+规则B（JSON+JS+img触发器） |
| **单一真相源** | 字段定义→引擎配置→协议文档→测试数据四处自动对齐，构建期断言 |

### 历史地位

醉猫的贡献不在理论也不在架构，而在**集成验证**。他踩出了大量「文档和现实的差距」，让后人不必再踩。

## 终章：影渲法 ShadowCast 2.0——洛璃提出的 Shadow DOM 隔离路线

**当前版本**：ShadowCast 2.0（吸收哨兵雷达法实测优点后的强化版）

### 这不是「超越」，是换了一条路

所有前人都走同一条路：**light DOM 注入**——在平台现有页面里创建组件，然后用各种补丁对抗平台的干扰。

雷达法需要一整层防御补丁（MutationObserver 哨兵、引号修复、font→span 净化、染色剥离、markdown 空白条三重防御……大约 15K+ 代码）才能正常跑，本质上是在 light DOM 里打补丁。

洛璃提出了影渲法：**不打补丁了。用 Shadow DOM 把整个组件隔离出去。**

Shadow DOM 是浏览器原生提供的隔离机制：
- 内部的 CSS 不外泄，外面的 CSS 不进来
- 不经过 markdown 管线 → 免疫空白条
- 不经过平台染色 → 免疫 font 标签注入
- 类名随便起，不需要前缀防冲突

雷达法 15K 的防御补丁，影渲法用一行 `box.attachShadow({mode:'open'})` 就解决了。

### 范式转换的代价

Shadow DOM 隔离也意味着引擎不能去「扫描历史气泡」做模糊特征嗅探——shadow 边界把它和外部 DOM 隔开了。所以：

> **在「模型自由涌现未知键名」这个能力上，雷达法至今没有被影渲法超越，也超越不了。**
> 这不是技术缺陷，是隔离的代价。选择隔离，就要接受 schema 预定义。

### ShadowCast 2.0 的核心强化

| 强化 | 1.0 的问题 | 2.0 的解决 |
|------|-----------|-----------|
| shadow→light DOM 降级链 | `attachShadow` 不可用时面板静默消失 | 自动 fallback 到 light DOM（`g3-`前缀类名 + CSS注document） |
| adoptedStyleSheets | 每条消息新建 `<style>` → N条消息N份相同CSS | 单张 `CSSStyleSheet` 跨气泡缓存，所有实例共享 |
| 事务式渲染 | 边建边挂，中途抛错留半个面板 | 内存建完→最后一步挂载，异常回退、数据完好 |
| key 同义词归一化 | 模型写 `HP` 和 `hp` 视为不同键 | `ALIAS` 表做归一化，`normKey()` 统一到标准 key |

## 第八章 ｜ Godcount —— 扔掉点火器

**代表作品**：《现代前端 UI 渲染架构开发指南》

### 核心贡献

从澄清的 KV-Robust 开始，整个社区默认了一条铁律：

> "MMD 上 `<script>` 标签不能用。必须用 `<img onerror>` 点火。"

这条铁律支撑了六位作者的所有方案。但铁律有「有效期」——它是平台封锁期的产物，而平台会变。

Godcount 是第一个抬头重新看了一眼现状的人。当前 MMD 的 `<script>` 标签已经解禁了。虽然 `document.currentScript` 仍然不可用（所以脚本不能 per-message 自定位），但全局 `<script>` 完全可以用来**注册一次 Web Component 类**，然后浏览器接管剩下的所有事情。

```
以前（影渲法 / 雷达法 / 所有前人）：
  每条消息带一份 img onerror → 一份完整的引擎代码副本
  10 条消息 = 10 份相同的 JS

Godcount 的方式：
  全局放一次 <script> → class ZLiveWidget extends HTMLElement
  每条消息只放一个 <z-live-widget></z-live-widget> 标签
  浏览器自动调用 connectedCallback() → 自动 attachShadow → 自动渲染
  10 条消息 = 1 份类定义 + 10 个轻量标签
```

### 工程细节

他的方案是一份完整的现代前端架构指南，要求三段正则配合：

| 正则 | 匹配式 | 作用 |
|------|--------|------|
| 正则 1（数据隐藏层） | `/\[#([^=\[\]#]+)=([^\[\]#]+)#\](?:\s|<br\s*\/?>)*/gi` | 把 `[#键名=键值#]` 包进隐藏 `<span class="z-live-data">` |
| 正则 2（UI 触发层） | `<GC_UI>` | 替换为 `<z-live-widget></z-live-widget>` 自定义标签 |
| 正则 3（全局引擎区） | `<GC_SCRIPT>` | 替换为 `<style>` + `<script>` 完整 Web Component 类定义 |

注意正则 3 放在**功能栏**而不是每轮对话中——这正是 `<script>` 全局注册的架构优势：类定义只注入一次，每条消息只需一个轻量标签。

### 与影渲法的异同

两者共享 Shadow DOM 隔离的根本优势，但在触发机制上分道扬镳：

| | 影渲法 | Godcount |
|---|---|---|
| Shadow DOM 隔离 | ✅ 手工 `attachShadow` | ✅ 浏览器 Web Components 生命周期 |
| 触发机制 | `img onerror` 点火 | `<script>` 全局注册 + 自定义标签自动实例化 |
| 引擎副本数 | N 条消息 = N 份 JS | N 条消息 = 1 份类定义 |
| 事件绑定 | onerror 单行 → `data-s` 存多行 → `eval` | 类方法里直接 `addEventListener` |
| 开发体验 | 被迫扭曲绕过平台限制 | 接近标准前端开发 |
| 兼容旧版 MMD | ✅ onerror 全版本兼容 | ❌ 要求新版平台 |

### 一个被忽略但致命的细节

Godcount 规范中特别指出：**Shadow DOM 不能阻止 CSS 可继承属性穿透边界。** `color`、`font-family` 这些属性会从宿主页面的白色文字漏进 shadow 内部，让你的面板白底白字什么都看不见。必须在 shadow 内部的 `<style>` 中为根容器强制声明 `color: #1c1c1e; font-family: sans-serif;`。

这个细节是影渲法文档中没有单独强调的——它对两个方案同样适用，是 Web 标准行为，不是 bug，但太容易踩。

### 内置的工程最佳实践

| 实践 | 实现 |
|------|------|
| 防重复注册 | `if (!window.ZLiveWidgetDefined)` —— 平台可能多次注入脚本 |
| 定时器集中管理 | `this.timers = []` + `disconnectedCallback` 统一清理 |
| 数据驱动主题 | 根据好感度/血量动态切换 shadow 内 CSS 变量 |
| 跨边界通信 | shadow 内按钮 → `document.querySelector('textarea')` → `dispatchEvent(new Event('input'))` |
| 移动端性能降级 | `@media (max-width: 768px)` 关闭动画和毛玻璃 |
| SVG 雷达图 | 纯 JS 计算坐标 + `createElementNS`，零依赖 |

### 历史地位

**Godcount 是第一个在 MMD 上用 Web Components 标准写法替代 onerror 点火器的人。** 从 KV-Robust 到影渲法，多位作者都在 `img onerror` 这条路上深耕。他是第一个看清「`<script>` 已经解禁」这个新现实的人。

他的方案代表了 MMD 状态栏的下一个技术阶段——onerror 点火器是封锁期的生存策略，Web Components 是开放后的标准路线。两者共享 Shadow DOM 隔离的优势，但触发机制的分野代表了两个不同的时代。

## 附篇 ｜ 五维技术纵深——给想深入理解的人

正文讲完了七个作者的故事。但如果你是一个开发者，拿到这几个方案摆在面前，你真正需要回答的问题是：**它们的本质区别在哪里？为什么后来者选择了这条路而不是那条？每个选择的代价是什么？**

以下从五个核心技术维度，把七个方案放在同一张解剖台上。

---

### 维度一：数据格式——"AI 到底输出什么"

这是最表层、但也是最直接影响 Token 消耗和 AI 出错概率的决策。

**柑硕**选择 HTML 属性式：`<div data-st nm="勇者" zy="hp:80/100">`。优点是结构清晰、字段与字段之间有明确的属性边界，前端用 `getAttribute` 逐个取值不会串。代价是**模型在每轮输出时都输出完整 HTML 标签**，哪怕只改一个 HP。Token 有多余支出。

**澄清 KV-Robust** 选择纯文本 KV：`ts::xxx;;name::张三;;points::200;;`。完全抛弃 HTML 标签，连 `<div>` 都不用。优点是极致精简——"纯数据，零标签"。代价是分隔符 `::` 和 `;;` 必须准确，模型一旦写错一个分号就会解析失败。而且缺少层级结构——所有字段平铺在一行里，复杂列表不得不塞进同一个 value 里。

**黑洞猫雷达法**选择 `[键名=键值]` 中括号语法：`[生命值=45/100] [武器=紫木法杖]`。这是唯一一种**不要求模型记住字段列表**的格式——模型自由发散新键名，引擎按特征字自动路由。代价是必须配一个信标转换器正则把中括号包进 `<span>`，而且严禁键值内部嵌套方括号（如 `[技能=[挥砍]]` 会直接炸）。

**澄清**回到柑硕的 HTML 属性路线，但加了 `<status>` 触发标记和更细的字段分类（`sthr`/`sopp`/`stsk`）。本质上是用之前的技术积累重新组织数据格式。

**Godcount**选择 `[#键名=键值#]` —— 在雷达法的中括号基础上加了 `#` 包裹，形式上更接近"模板变量"的直觉。

**数据格式的核心权衡：模型自由度 vs 解析稳定性。**

```
模型自由度 高 ←→ 解析稳定性 高

雷达法 [键=值]                KV-Robust :: / ;;
（模型可自由发散新键名）       （分隔符严格，但层级扁平）

Godcount [#键=值#]            柑硕 / 澄清 HTML属性
（中括号 + # 双重边界）        （getAttribute 逐个取值，不串不丢）
```

柑硕 / 澄清的路线是最稳的——`getAttribute` 不存在歧义。但雷达法的路线是模型最自由的——不需要预定义字段就能路由。这两个方向至今不可兼得。

---

### 维度二：触发机制——"代码什么时候跑、怎么跑"

这是一个被新手严重低估、却是所有方案中最容易翻车的维度。

**所有 2024 年前后的方案**统一使用 `img onerror` 点火。原理：放一张 `<img src="x">`，图片加载失败时浏览器自动执行 onerror 里的 JS。这不是"优雅"，这是在那时 `<script>` 被禁的条件下**唯一的选择**。

onerror 点火带来了三个连锁代价：

1. **JS 必须单行压缩**（澄清 KV-Robust 时代发现）——多行代码会被平台 CSP 截断。
2. **每条消息携带一份完整引擎副本**——10 条消息 = 10 份相同的 JS。不是 bug，是 waste。
3. **触发顺序不可控**（锐发现并解决）——页面打开时所有历史消息的 onerror 几乎同时点火，但执行顺序不保证和回复时间顺序一致。

醉猫后来发现了两个绕过单行限制的方法：
- `data-s` 属性可以存多行 JS
- `<script type="text/plain">` 可以存多行 JS（但**绝对不能有 `
` 字符**——这是醉猫踩出来的零级红线，eval 会静默失败不报错）

**Godcount 是第一个跳出 onerror 范式的人。** 他用 `<script>` 全局注册 Web Component 类，让浏览器用 `connectedCallback` 生命周期自动逐条实例化。代码只加载一次，每条消息只需一个轻量的自定义标签。

但这条路的前提是**新版 MMD 已经解禁了 `<script>` 标签**。旧版 MMD 上这条路线走不通——这也是影渲法保留 onerror 机制的原因：它要兼容旧版平台。

```
触发机制的演变本质：

澄清 KV-Robust 时代：  被迫选择 onerror（唯一能跑的方式）
醉猫时代：      挖掘 onerror 的极限（data-s、script plain、
 红线）
Godcount 时代：  发现铁律已过期，切换到 Web Components 标准机制
影渲法：        保留 onerror 作为全版本兼容选项
```

---

### 维度三：DOM 渲染策略——"代码怎么变成界面"

三个派别。

**派别 A：预制骨架 + 正则替换（KV-Robust、柑硕、澄清）**

```html
<!-- 骨架写死在 replaceString 里 -->
<span class="ds-val-name">加载中...</span>
<span class="ds-val-points">加载中...</span>
<!-- onerror 点火后 JS 找到这些 span，改 textContent -->
```

优点是简单直观。缺点是骨架和代码耦合——新增一个字段要同时改 HTML 模板和 JS 更新逻辑，两处对齐。

**派别 B：内存动态装配 + 一次性挂载（雷达法）**

```javascript
// 不在页面上改任何现有节点
var panel = document.createElement('div');
var nameRow = document.createElement('div');
nameRow.textContent = kv['名字'];
panel.appendChild(nameRow);
// ...全部拼完
box.appendChild(panel);  // 最后一步挂载
```

优点是**免疫平台排版引擎篡改**——所有节点在独立内存中创建，平台干预不到。代价是引擎代码量显著增加（~13K），因为需要完整的 DOM 构建逻辑。

**派别 C：Shadow DOM 隔离（影渲法、Godcount）**

```javascript
var shadow = box.attachShadow({mode: 'open'});
// 在 shadow root 里渲染，外部看不到、管不着
```

优点是**一劳永逸**——不需要防御补丁（空白条、染色、font 注入、类名冲突全部免疫）。代价是**牺牲了跨气泡扫描能力**——shadow 边界让引擎无法读相邻消息的数据做自由键名嗅探。

**DOM 渲染策略的技术分岔点：**

```
              ┌─ light DOM 预制骨架（最简单）
              │   柑硕 / KV-Robust / 澄清
              │
渲染策略 ─────┼─ light DOM 动态装配（抗平台篡改）
              │   雷达法（~13K 引擎 + 防御补丁）
              │
              └─ Shadow DOM 隔离（一劳永逸）
                  影渲法（onerror 点火）/ Godcount（Web Components）
```

选择 light DOM 动态装配，就要接受防御补丁的成本。选择 Shadow DOM，就要接受 schema 预定义的约束。没有免费午餐。

### 维度四：数据继承与生命周期——"信息该活多久"

柑硕第一个提出问题："模型没输出的字段怎么办？"他的答案是向上遍历 DOM —— `querySelectorAll('.status-bar')` 然后倒序找。**这个思路至今仍被使用**（雷达法的全量历史扫描本质上也是这个思路的不同实现）。

但柑硕的继承是**二元的**——要么继承，要么不继承。雷达法把它细化成了一个**五级体系**：

| 级别 | 继承策略 | 引擎行为 |
|------|---------|---------|
| 一类 全局锚点 | 固态底座 | 缺失时向历史兜底 |
| 二类 高频变量 | 固态底座 | 同上 |
| 三类 后台暗流 | 不渲染 | 解析但不显示 |
| 四类 场景快照 | **液态快照** | **缺失即销毁，不兜底** |
| 五类 低频冗余 | 固态底座 | 缺失时兜底 |

**第四类数据的"不兜底"是雷达法最深的洞察。** 柑硕时代的继承思维是"越多越好"——能继承的都继承。雷达法发现**有些数据的继承本身就是污染**。高刺激感官词汇残留在长线上下文中会扭曲模型的推理。

影渲法的双轨代谢（`volatile` 标记 → `inherit:false`）直接从雷达法搬过来，用 `FIELDS` 定义中的 `volatile:True` 控制。Godcount 在 Web Component 的 `extractData()` 中同样可以按这个逻辑实现——但他没有在规范中展开这一点，这是他留给后来者的补全空间。

**数据生命周期的认知跃迁：**

```
柑硕：        "没输出的字段 → 继承"        （二元思维）
      ↓
雷达法：      "先分类，再决定哪些继承、哪些销毁"  （五级思维）
      ↓
影渲法/Godcount：  继承雷达法的五级分类，工程化落地
```

### 维度五：平台对抗策略——"怎么在敌意环境里活下来"

这是整个 MMD 状态栏史上最硬核的一条线。

**澄清 KV-Robust 时代**的对抗是被动的——发现一个限制绕一个限制。`<script>` 被封 → 用 onerror。多行截断 → 单行压缩。`<` 被转义 → 改写为 `!=`。这时的生存策略是**躲避**——绕过平台的审查而不是正面对抗。

**黑洞猫雷达法时代**的对抗变为主动——引擎内置了完整的防御体系：

- **MutationObserver 哨兵**：持续监控 DOM，一旦发现平台强插的 font 标签立即剥离
- **引号修复函数**：修正被平台 CSP 篡改的双引号
- **markdown 空白条三重防御**：源头压平 + 防御 CSS（`p:empty{display:none}`） + 信标尾吞
- **染色剥离**：平台在文本中注入的颜色标签需要被清理
- **虚拟 DOM 劫持对抗**：2.5s 短程探针自检，被抹了就原地重建
- **作用域逃逸防御**：编辑预览框内引擎可能扫到全页数据，需要层级阈值硬收缩

总计约 **15K** 的防御代码。不是做业务逻辑，是在和平台打架。

**影渲法（及 Godcount）**说：**不打补丁了。换介质。**

Shadow DOM 不是"更好的补丁"。它是**浏览器级别的隔离**——markdown 渲染管线运行在 light DOM 层级，shadow root 内部完全不受其影响。雷达法需要用 15K 补丁对抗的所有问题（空白条、染色、font 注入、类名冲突），在 shadow root 内**自动免疫**。

影渲法把 15K 的防御代码缩减为一行：

```javascript
box.attachShadow({mode: 'open'});
```

但这不意味着雷达法的对抗经验失去了价值。相反，它告诉我们一个更深的原则：**如果一个问题需要超过 10K 的对抗代码才能解决，真正的问题可能不在于「对抗得不够好」，而在于「选错了战场」。**

```
平台对抗策略的分岔：

              ┌─ 躲避（被动绕过限制）
              │   KV-Robust: onerror / 单行压缩 / i!=length
              │
对抗策略 ─────┼─ 对抗（主动防御补丁）
              │   雷达法: ~15K 防御代码（哨兵/修复/剥离/自检）
              │
              └─ 隔离（换介质，不打架）
                  影渲法: attachShadow → 一行解决 / Godcount: Web Components
```

## 横切对比：谁在什么场景下仍然是最佳选择

| 场景 | 最佳方案 | 理由 |
|------|----------|------|
| 只有 5 个固定字段，追求极简 | **柑硕** | 代码最短、最易理解、零依赖、至今能跑 |
| 需要模型自由发散新键名（如自创装备/技能） | **雷达法** | 模糊特征嗅探自动路由，影渲法和 Godcount 做不到 |
| 追求隔离省心，不想和平台对抗 | **影渲法** 或 **Godcount** | 共享 Shadow DOM 隔离优势 |
| 追求代码整洁、标准前端开发体验 | **Godcount** | Web Components 原生生命周期，无 onerror hack |
| 兼容旧版 MMD（`<script>` 仍禁用） | **影渲法** | onerror 全版本兼容 |
| 需要跨回复全局 UI（地图、侧边栏、弹窗） | **AGENT 架构** | 五类文件 + 六步链 + 最新仲裁，与具体渲染技术无关 |
| 快速原型、最简单的状态面板 | **KV V4.0 或 $field** | 零 JS 或最少 JS，三段固定模板 |
| 做全局美化（改平台原有元素样式） | **传统穿透方案** | Shadow DOM 隔离与全局穿透目的相反 |

## 结语：这不是一条进化链，是一个工具箱

```
柑硕                    —— 数据和视图，从此不再是一家
  ↓
澄清 KV-Robust         —— 在雷区里，一寸一寸试出来的生路
  ↓
黑洞猫 雷达法          —— 「不是所有记忆都值得保留」
  ↓
澄清                   —— 第一次，有人把不同的路拼在了一起
  ↓
锐 AGENT               —— 从系统的高度，重新审视一切
  ↓
醉猫                   —— 用秒表和卡尺，测出了真实的边界
  ↓
影渲法 ShadowCast      —— 「不打补丁了。隔离。」
  ↓
Godcount               —— 「点火器。也可以不用了。」
```

**这不是一条进化链。**

每一步都在前人的地基上增加新的能力。但没有人因此过时。柑硕的五字段面板仍然是最简解。雷达法的模糊嗅探仍然是唯一能处理自由键名的方案。锐的最新仲裁仍然是任何复杂注入都绕不开的工程问题。

你面对一个具体需求时，不是选「最新的那个」。

是选「最匹配的那个」。
