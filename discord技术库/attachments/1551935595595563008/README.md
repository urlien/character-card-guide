# 角色卡批量立绘 / 差分生图工作流

> **一句话**：用 AI Agent 直接驱动 NovelAI 批量生成演出立绘，是压低整套舞台演出流程成本的关键。

把这件事工程化之后，「给一个角色画一百张同人差分」就从抽卡作坊，变成一条**可控、可复跑、可交接**的流水线。

这套流程是在本地长期做角色卡（AI 对话角色卡，需要成套立绘 + 表情 / 姿势 / 服装差分）的过程中沉淀出来的，
跑过的最大批量是 **62 个角色 / 488 张差分一次过**，以及单卡 **166 张补图**的全自动后处理。
它不依赖任何特定平台的私有功能，只需要一个能批量调用的文生图后端 + 一个本地抠图模型。

下面讲的是**方法**，不是某一套提示词。所有提示词示例都做了抽象化处理。

**许可证**：[MIT](LICENSE)

---

## 一、它解决什么问题

手工生图的痛点不是「画不好」，而是：

| 痛点 | 表现 |
| :--- | :--- |
| **角色漂移** | 同一角色 100 张图，脸/发色/瞳色越来越不像 |
| **拼接矛盾** | 每一段提示词单独看都对，拼起来互相压制（闭眼 × 瞳色、全裸 × 上衣） |
| **账目丢失** | 图生出来了，但 seed / 提示词 / 负面没了，再也复现不了 |
| **背景不干净** | 生成的图带背景，抠图抠不干净，边缘一圈毛边 |
| **修不动** | 用户说「第 3 张最好，以它为基础微改」，结果整批重做 |
| **搬不动** | Agent 只能写提示词，真正出图还得人工一张张粘进软件——**这就是无法批量的根因** |

这套流水线的每一条设计，都对应上表的一行。

---

## 二、五条设计原则

1. **提示词分层解耦** —— 一条提示词被切成五层，差分只允许改最下面三层。
2. **角色锁定 = seed + 外貌基底双重锚定** —— 二者缺一，角色必漂。
3. **门禁前移** —— 在发批次之前用代码查出矛盾，而不是生成完 120 张再靠肉眼发现。
4. **生图能力对 Agent 开放** —— 后端暴露本机控制接口，Agent 只做编排与核验，不做生图推理。
5. **视觉验收归人，机器只保证像素与账目** —— 脚本只做 alpha 校验和文件计数，从不「审图」。

---

## 三、总体流程

```
参数档案  →  五层组装  →  生成前门禁  →  批量生图  →  后处理  →  人审上架
 (JSON)      (拼串)       (冲突检查)     (串行落盘)    (抠图/体检)   (挑图/上传)
                                              ▲
                                  AI Agent 驱动（详见第四节）
```

前三个环节是**准备**（把事情算清楚），第四个环节是**执行**（把事情做出来）。
执行这一段由 AI Agent 接管——**这是整条流程能「批量快速」的根本原因**，详见第四节。

每个环节都有一个**单一事实源**：后面的环节一律从它派生，禁止复制粘贴。
这是整条流水线能复跑的关键——**改了源头就重跑整条链，而不是手改某一环的产物**。

## 四、让 AI Agent 接管生图（批量化提速的关键）

前三个环节产出的都是**数据**——档案、批次 JSON、门禁清单。
把它们真正变成几百张图，靠的是让 **AI Agent 直接驱动生图后端**，
而不是让 Agent 写提示词、再人工一张张粘进生图软件。

这一节是整个流程里「快」的来源。**没有它，前面所有自动化都只是半自动。**

### 4.1 核心思路：Agent 只做编排，不做生图

一条常见的错误链路是：

```
Agent → 生图工具（内含一个 LLM）→ LLM 理解提示词 → 调生图 API
```

中间那层 LLM 又慢、又贵、又不稳定：它会**审核拒单**（整批直接卡住）、
每张多花十几秒纯推理、还会因为网络抖动误判失败而**重发双批**。

正确链路是把 LLM 从执行链里彻底拿掉，让**确定性代码**走完全程：

```
Agent（组装批次 / 调接口 / 核验落盘）
  ↓  确定性指令
生图后端的控制服务（权限 / 计费 / 审批 / 审计）
  ↓
NovelAI API
```

Agent 在这里的角色是**批次组装器 + 调度器 + 账簿**，不是「提示词解释器」。

### 4.2 四段式架构

```
┌──────────────────────────────────────────────────────────┐
│  Agent 层：WorkBuddy / DeepSeek Harness / Antigravity …   │
└────────────────┬─────────────────────────────────────────┘
      ① 工具调用  │  ② 命令行子进程
┌────────────────▼─────────────────────────────────────────┐
│  适配层：Agent 插件  或  独立 CLI                         │
└────────────────┬─────────────────────────────────────────┘
      ③ HTTP loopback + Bearer token
┌────────────────▼─────────────────────────────────────────┐
│  生图应用内的 Agent 控制服务（control bridge）             │
└────────────────┬─────────────────────────────────────────┘
      ④ 应用自身的权限 / 计费估算 / 应用内审批 / 审计
┌────────────────▼─────────────────────────────────────────┐
│  生图服务商 API（如 NovelAI）                             │
└──────────────────────────────────────────────────────────┘
```

**这一层是通用的**：换 Agent 不用改生图逻辑，换生图后端也不用改 Agent。

### 4.3 后端要暴露什么：控制桥

生图应用（桌面端）需要开一个**只绑本机回环**的控制接口。以我们用的实现为例：

**① 一次性发现文件**

应用启动时在系统支持目录写入一份描述文件，退出时删除：

```
%APPDATA%\<app-id>\agent\agent-control-v1.json
```

```jsonc
{
  "protocol": "aaalice-agent-control",
  "version": "1",
  "base_url": "http://127.0.0.1:<随机端口>",
  "token": "<bearer token>"
}
```

> ⭐ **端口是随机的、文件是活的、每次启动都不同。**
> 所以适配层**绝不能硬编码 URL 和 token**——必须在每次调用时懒加载这份文件
> （我们设了 5 秒的缓存 TTL）。
> 也正因如此，**这份文件不能进 Git、日志、截图**，它是本机凭据。

**② 端点**

| 端点 | 作用 |
| :--- | :--- |
| `GET /v1/capabilities` | 命令清单 |
| `GET /v1/status` | 服务运行状态 |
| `POST /v1/commands` | 执行一条命令 |

**③ 命令信封**

```jsonc
POST /v1/commands
Authorization: Bearer <token>

{
  "protocol": "aaalice-agent-control",
  "version": "1",
  "request_id": "<uuid>",
  "method": "generation.submit",
  "params": { },
  "idempotency_key": "<确定性键>"     // 写操作必带
}
```

响应统一为 `{ ok, protocol, version, result }` 或 `{ ok: false, error: { code, message, details } }`。

**客户端侧建议加的三道校验**（我们实测都必要）：
- 协议名 + 版本必须严格匹配，否则报协议错误；
- URL **必须是 http + 回环地址**（`localhost` / `127.*` / `::1`），否则拒绝——防止 token 被外发；
- **响应体加大小上限**（我们设 4 MiB），并加单命令超时（我们用 15 分钟）。

**④ 命令族**

控制桥**不重新实现**生图能力，而是把应用内已有的能力暴露成方法：

| 命令 | 作用 |
| :--- | :--- |
| `settings.read` / `settings.update` | 读写生成参数（模型 / 步数 / scale / 采样器 / 噪声调度） |
| `prepare` | 出准备事务 id + **预估消耗**，**不调 provider** |
| `inspect` / `cancel_preparation` | 查看 / 取消准备事务（取消是破坏性操作，应用内会弹审批） |
| `submit` | 提交并等待，走应用原生管线（限流重试 / 冷却 / 自动落盘） |
| `save` | 按资源引用落盘到显式路径（**排他创建，绝不覆盖**） |
| `status` | 管线进度与队列统计 |
| `abort` | 取消审批弹窗 + 停止原生生成 |

⚠️ **必须单独设计一条「并发白名单」**：长命令（submit）执行期间，
`status` / `abort` / `settings.read` 这几个必须能插队执行，否则批次卡住时连进度都查不了。

### 4.4 两条接入路线

| | **插件形态** | **CLI 形态** |
| :--- | :--- | :--- |
| 形态 | Agent 的原生工具（tool call） | 一次子进程命令行调用 |
| 代表 | 给 DeepSeek Harness 写的插件 | 随工具链附带的 `nai_direct.mjs` |
| 优点 | Agent 直接拿到结构化结果，可编排、可中断、可并发查状态 | **零适配**：任何能跑 shell 的 Agent 立刻可用 |
| 缺点 | 要为每个 Agent 写插件；改代码后要重新同步依赖，否则两边漂移 | 输出要靠日志文件读；进程管理自己管 |
| 适用 | 固定主力 Agent | 多 Agent 混用 / 快速试 / 交叉验证 |

**我们两条都留了**——插件是主力，CLI 是通用逃生门。
WorkBuddy、Antigravity 这类没有专用插件的 Agent，走的就是 CLI：

```bash
# 单张验证链路
node nai_direct.mjs single --prompt "<正向>" --file "test.png" --seed 564001 --save-dir "<目录>"

# 解析派发文本 → 批次 JSON
node nai_direct.mjs parse "<派发文本.txt>" --out "<批次.json>"

# 跑批次（引擎自带幂等：中断后重跑自动跳过已落盘张）
node nai_direct.mjs batch --tasks "<批次.json>" --save-dir "<输出目录>" > run.log 2>&1

# 查状态 / 终止
node nai_direct.mjs status
node nai_direct.mjs abort
```

> ⭐ 关键：**CLI 让「换 Agent」的成本降到 0。**
> Agent 只负责生成 `tasks.json`（五层组装 + 门禁的产物）和读取落盘结果，
> 生图这一段完全是黑盒，任何 Agent 都能接管。

### 4.5 直连到底快在哪

| 指标 | LLM 中转链路 | 直连链路 |
| :--- | :--- | :--- |
| 每张的 LLM 推理开销 | ~15s | **0** |
| 审核拒单 | LLM 可能整批拒掉 | 无 LLM 参与；提示词清理是**确定性代码**，不裁决内容 |
| 重复存图 | 同 resourceId 可能重复落盘 | save 与本次 submit 返回的引用**一一对应** + 批内哈希查重 |
| 网络抖动 | 假阴性 → 误判失败 → 重发双批 | `idempotency_key` 服务端幂等回放，同 key 绝不重复出图 |
| 串行保证 | 靠 LLM「自觉」 | 引擎硬编码逐张串行，服务端命令队列再兜底一层 |
| 本体耗时 | — | submit 约 9s，save 约 20ms |

### 4.6 安全与成本边界（必须守住）

| 边界 | 做法 |
| :--- | :--- |
| **网络** | 接口只绑回环地址；客户端**主动拒绝**非回环 URL |
| **凭据** | 每请求 Bearer token；发现文件只应授予本机 Agent 进程读取；**不进仓库 / 日志 / 截图** |
| **计费** | 写操作前先 `prepare` 估算消耗；**超过阈值直接拒绝**，必须显式授权才放行 |
| **审批** | 生成与破坏性命令**仍走应用自身的应用内审批**，适配层不复制、不绕过这一层 |
| **审计** | 所有命令落审计日志（应用侧审计文件） |
| **禁审图** | 工具返回值**只含** 文件名 / seed / 尺寸 / 字节 / 成败，绝不生成画面描述 |

> **适配层只做协议转换，不做权限判断。** 权限、计费、审批、审计永远由生图应用自己把关——
> 这是「让 Agent 自动跑几百张图」这件事能被接受的前提。

### 4.7 接一个新 Agent 的清单

1. 生图应用以**带控制开关**的方式构建并启动
   （Flutter 类项目：`--dart-define=ENABLE_AGENT_CONTROL=true`）。
2. 确认发现文件已生成（含 `base_url` + `token`）。
3. 二选一：装 Agent 插件（`plugin add file:<插件目录>`），或直接指向 CLI。
4. 先用 `single` **跑 1 张**验证整条链路（含落盘核验）。
5. 再跑 `batch`，并且**单角色单批 ≤ 8 张**、批间核验落盘；新角色先跑 2~3 张试角色一致性。

### 4.8 这一层的坑

| 坑 | 表现 | 对策 |
| :--- | :--- | :--- |
| 应用没带控制开关 | 进程活着，但端口没监听 | 按 §4.7 第 1 步重新构建 |
| 硬编码地址 | 重启后连不上 | 端口随机 + 文件退出即删 → **每次懒加载** |
| CLI `batch` 只传了一半参数 | 直接打印用法退出，不执行 | `--tasks` 与 `--save-dir` **必须同时出现** |
| CLI 输出被管道吞掉 | 无输出、非 0 退出码，但**批次其实跑完了** | stdout **重定向到日志文件**再读；成败以日志 + 落盘文件为准 |
| Agent 侧插件序列化报错 | 报「响应不是无损 JSON」 | 批次可能**已启动** → 用 CLI `status` 查证，后续走 CLI |
| 改插件源码没同步 | 行为与预期不符 | 改源目录后必须重新安装依赖同步，两边不自动跟随 |

## 五、环节详解

### 环节 1 ｜ 角色参数档案

把「一个角色的视觉身份」固化成一份 JSON，而不是散落在提示词字符串里。

```jsonc
{
  "name": "角色名",
  "seed": 1234567890,              // 定稿立绘的 seed，全卡差分共用
  "base_prompt": "...",            // 外貌基底（锁定区，差分一字不动）
  "color_anchor": {                // 主色锚定，缺色的角色必须在这里补齐
    "hair": "silver hair",
    "eyes": "wine red eyes",
    "outfit": "black cardigan"
  },
  "gender_group": "female",        // 决定负面词表用哪一套
  "skip": false
}
```

**为什么要有 color_anchor**：模型对「没有明确颜色」的服装会自行发挥。
实测过一次：补图脚本没有重新应用颜色回填，一批绿衣角色全变成了红衣。

> ⚠️ 档案里 `- 正向提示词:` 这类行有被工具链截断的风险，解析时要能识别并拼接续尾，不要静默截断。

### 环节 2 ｜ 五层提示词组装

```
[1 风格画质]  masterpiece, best quality, very aesthetic, absurdres
[2 外貌基底]  发色 · 瞳色 · 体型 · 五官          ← 锁定区
[3 服装配饰]  原服装基底 + 状态派生（掀衣/褪裤）  ← 变量区
[4 动作姿态]  每张唯一的姿势                    ← 变量区
[5 表情镜头]  表情 · 视角 · 构图                ← 变量区
```

三条硬规则：

- **锁定区一字不动。** 差分 = 定稿立绘的原文基底 + 受控修改点，其余字符级一致。
- **姿势段要前移。** 把姿态词插在主体身份词（`1girl` / `1boy`）之后，
  比塞在末尾权重高得多——埋在末尾会被服装与体型权重压平，这是「姿势总不听话」的结构性原因。
- **组装后保序去重。** 姿势段和服装段经常出现同一个 tag，重复 tag 会**加倍权重**把构图带偏。

**服装状态派生表**（半裸比全裸稳得多）：

| 状态 | 写法方向 | 露出 |
| :--- | :--- | :--- |
| 露款 | 保留原服装 + 拉开领口 / 提高开叉 | 不裸 |
| 衣襟敞开 | 衣襟拉开 + 胸部露出 | 上身 |
| 裙掀到腰 | 裙摆上提 + 下身露出 | 下身 |
| 半挂肩 | 衣服滑落肩头 | 部分 |
| 上下全开 | 上面两组叠加（**仍穿服装**） | 全 |

同时负面**反向封死**「完全裸体」类词，逼模型不许把衣服脱光。

> ⭐ **题材服装符号必须保留**：汉服 / 旗袍 / 制服 / 和服这类卡，差分**禁止走完全裸体**——
> 否则角色唯一的视觉辨识度整个丢掉，用户会成批删图。实测：首批 60 张里被删 5 张，根因就是全裸。

### 环节 3 ｜ 生成前门禁

这是整套流程里**回报率最高**的一环。两条检查：

#### 冲突检查（tag 级）

把正向按逗号切分、剥掉权重（`(tag:1.2)` → `tag`）后**逐对判定**，
不要拿整串做正则——切干净了判据才写得准。

```python
def norm_tags(prompt):
    out = []
    for t in prompt.split(","):
        t = t.strip().lower()
        t = re.sub(r"^\((.*?)(?::[\d.]+)?\)$", r"\1", t)   # 剥权重
        if t:
            out.append(t)
    return out
```

规则表 = `(编号, 说明, 级别, A正则, B正则, 豁免正则)`，**A 命中且 B 命中**即报警。
支持在 B 正则里用 `\1` 引用 A 的捕获组，用于同名词比对
（`sports bra removed` × `sports bra` = 同一件衣服又要又不要）。

实测抓到的真冲突类型：
- `closed eyes` + `wine red eyes` —— 瞳色是角色锁定第一要素，被闭眼遮住等于白写
- 「完全裸体」+ 任意上衣 —— 又要光又要穿，出图必脏
- `standing` + `sitting` —— 姿势自相矛盾
- 基底 `modest breasts` + 差分追加 `plump breasts` —— **互相压制**（用户反馈「胸小」的根因）
- 基底仍列某件衣服 + 姿势段说已脱下

> ⚠️ **负向用例必须成套**：每条规则都要有「应触发」+「不应触发」两类用例，
> 判定 100% 正确才能信这个检查器。没有负向用例的规则形同虚设。
> 实测某卡 21 条互斥规则：负向用例 15/15 全对，实际批次 ERROR 0。

**可跑的示例实现见 [`tools/check_conflicts.py`](tools/check_conflicts.py)**——12 条互斥规则 + 正负向重叠检查，
自带 20 条用例集：

```bash
python tools/check_conflicts.py --self-test                 # 20/20 用例必须全过
python tools/check_conflicts.py --positive "<正向>" -n "<负面>"
python tools/check_conflicts.py --batch <batch.json>        # 逐条报 ERROR/WARN，有 ERROR 则退出码 1
```

> ⚠️ **写这个检查器时踩到的一个真实坑，正好印证本节的教训**：
> 最初用 `re.Match.expand()` 来展开 B 正则里的 `\1` 反向引用——它会**把 `\b`、`\w` 当非法转义抛错**，
> 而这个错被 `try/except` 吞掉后，**13 条规则全部静默失效**、自测 13/13 全 FAIL 才暴露。
> 正解是自己替换反向引用（只处理 `\1`..`\9`，其余原样保留）。
>
> **教训**：任何 `try/except` 包住的判定逻辑，都必须有负向用例证明它「真的会报错」。

#### 题材硬性断言

某些规格是**数字级**的（权重、词表长度），写成散文就一定会在组装时漏。
把可判定的部分写成断言，组装完批次立刻跑：

```python
assert "(tag:1.4)" in pos        # 权重写错会明显偏移表现
assert "modifier" in pos         # 漏写这个修饰词，模型会走默认行为
for w in NEGATIVE_BLOCKLIST:     # 负面封锁词一个都不能少
    assert w in neg, w
```

> ⚠️ **自检脚本自己也会写错，而且写错同样静默通过。**
> 我们有过一次真实翻车：自检脚本里的分组名写成了**另一张卡**的姿势名，
> 6 个词永远匹配不到，跑一遍全 PASS 其实是根本没在检查。
>
> **所以自检写完必须做负向验证**：故意塞一条坏样本，确认它真的会报错；
> 再跑一遍真实批次确认全 PASS。**没被坏样本验证过的自检，不算自检。**

#### 迭代纪律（血泪）

1. ⭐ **单轮改动不超过 2 个变量。** 用户认的是**整体观感**，不是 tag 数量。
   实测一次改 6 个被接受，下一轮再叠 3 个就被判「观感丢失」。改动变量越多，越只能整轮推翻。
2. **说「以某张为底子微改」就**必须沿用那张的原 seed，prompt 除改动点外一字不动。
   换 seed 重写 = 重做，不是微改。
3. **强化 tag 用同 seed 多档变体法**：一个 seed 跑 5 张，只改强化组强度（轻/中/强/极致），
   让用户挑档位——比让用户抽象描述「再好看点」高效得多。
4. **一次只改一个方向。**「表情不对」和「构图不对」分轮解决，别在同一轮里同时动表情段和姿势段。
5. **被否的整轮归档不删**（移进 `_备选_第N轮\`）——用户常回头说「还是第 N 轮那张好」。

### 环节 4 ｜ 批量生图

直连生图后端的控制接口，**绕过前端 / 智能体中转**，逐张串行执行：

```
prepare → submit → save → 本地落盘核验 → 下一张
```

四条铁律：

| 铁律 | 原因 |
| :--- | :--- |
| **串行**，绝不并行 submit | 并行提交会互相中断 |
| **幂等**：submit/save 带 idempotency_key | 同 key 重试不出双图 |
| **默认跳过已存在文件** | 断点续跑，重跑不浪费额度 |
| **只信本地落盘核验** | 数文件 / 查大小 / 比对字节，后端汇报只作参考 |

其余要点：

- **参数按 task 传，不要放全局 settings。** 竖版立绘和横版地图可以在同一批次里跑。
- **禁审图**：工具的输出与报告只含 文件名 / seed / 尺寸 / 字节 / 成败，不读图。
  视觉验收永远归人。
- **CLI 输出必须重定向到日志文件再读。** 实测经管道时整个 stdout 会被吞掉，
  但批次实际已成功跑完——判断成败永远以**日志文件 + 本地落盘文件**为准。
- **收费保护默认开启**：估算消耗 > 0 时直接拒绝，必须显式授权才放行。
- **报「额度不足」时先查登录态。** 实测一次整批报收费，误判为额度耗尽，
  真实根因是账号掉登录——重新登录后同批次立刻 0 消耗跑通。
  排查顺序：**① 登录状态 → ② 模型/尺寸是否免费档 → ③ 当日额度是否耗尽**。

**透明的两条路线**（模型能力事实，别试错）：

- **透明直出**：只有部分模型版本原生支持「透明背景」参数。必须同时：
  正向末尾加 `simple background`、负面追加场景防御词（`location, scenery, sky, clouds, ...`）。
- **白底 + 本地抠图**：其余模型只能走这条——白底生成，再本地抠图。
  ⚠️ 不支持透出的模型强行传透明参数，只会得到 **alpha 全 255 的假 RGBA**。

### 环节 5 ｜ 后处理

标准顺序（**顺序不能换**）：

```
① 参数归档      ← 必须在转透明之前！
② 白底备份      ← copy 不 move，白底版是唯一救命底稿
③ 文字分割抠图
④ alpha 边缘清理 + 重映射
⑤ 拷回覆盖
⑥ 统计复验
⑦ 缩略图刷新
```

> ⚠️ **① 必须在最前**：转透明会剥离 PNG 的 tEXt 元数据，
> 一旦转换过，seed / 提示词就再也取不回来了。

#### 抠图路线怎么选

| 优先级 | 方式 | 适用 |
| :--- | :--- | :--- |
| 🥇 首选 | **文字分割模型**（如 IS-Net-Anime，ONNX 本地推理） | 全部场景，不依赖背景颜色，识别的是「人物」而非「白色」 |
| 🥈 备选 | **四边泛洪（BFS）** | 仅当背景绝对纯白 + 无投影 + 构图简单 |

**别指望「白底就上泛洪」这条捷径。** 泛洪有三个失败模式：

1. **封闭区域留白块** —— 泛洪从四边出发，清不掉被身体围住的区域（臂弯、腿间、腰侧）。
   而**四角 alpha 校验查不出内部残留**。
2. **浅灰地板阴影清不掉**（占比最大）—— 生成图几乎都带一层浅灰投影（≈230~240），
   阈值判不成「白」，整片阴影原样留下。**「背景本来就是纯白」这个前提本身就不成立。**
3. **把皮肤高光当背景打洞** —— 大腿/胸口的镜面高光亮度也可能 ≥240，
   与外部连通就被一起泛洪成透明，主体上出现灰洞。

> ⭐ **决定性论据**：**背景阴影与皮肤高光的亮度是重叠的** ——
> 没有任何单一阈值能同时「清掉阴影」和「保住高光」。
> 只有语义分割能把它们分开。

**怎么用可复现的 A/B 法判定泛洪到底能不能用**：拿分割模型的结果当裁判，逐像素比对 alpha 通道——
`漏抠` = 裁判判背景而泛洪不透明；`误砍` = 裁判判主体而泛洪已透明。
两项占主体面积都 ≤0.05% 才算该张干净。
> 实测一次：候选 85 张里**只有 7 张干净**，漏抠中位 7.4%、最坏 11.9% → 全批改回分割模型。

| 体量参考 | 速度 |
| :--- | :--- |
| 分割模型 | ~30s/张（166 张 ≈ 80 分钟） |
| 泛洪 | ~0.38s/张（快 80 倍，但质量不可控） |

**alpha 清理三参数**（治分割模型软 mask 的宽半透明光晕）：

| 参数 | 作用 |
| :--- | :--- |
| `--threshold 128` | 全图 alpha < 128 的极弱残留清零 |
| `--edge 12 --edge-threshold 230` | **外圈 12px 用更激进阈值**（背景残留只出现在外圈，主体 alpha=255 不受影响） |
| `--remap 100,220` | alpha 重映射：≤100→0、≥220→255、中间线性拉伸 |

实测效果：半透明占比 **11.59% → 3.91%**；166 张批量清理 47 秒跑完。

**验收双指标**：
1. **四角 alpha 全 < 100**（任一角 ≥250 = 白底残留）
2. **外圈 12px 半透明占比 < 5%**

> ⚠️ **alpha 清理不能重复施加**：对已经清理过的图再跑一次会**二次硬化边缘**。
> 只处理本轮新抠出来的文件，别整目录重跑。

### 环节 6 ｜ 人审与上架

**不要让用户逐个点开 100+ 张文件。** 拼一张 contact sheet：

```
python tools/make_contact_sheet.py <目录> -o 审图.jpg --cols 8 --cell 240 --title "..."
```

- 透明图合成到**浅灰底**——白边 / 抠图瑕疵在这种底上最容易看出来
- 每格标序号 + 名字，用户可以直接说「删第 3、7 张」

**⚠️ 铁律：不要自动上传图床。**
素材生成与校验完毕后交由**用户本人**过一遍、删掉不合适的、再上传。
上传是**不可轻易回退的外部账号操作**——即使是自动化脚本能做到，也不该跳过人工审核。
（我们跳过审核自动传过一次 120 张，被用户指正。）

删图后的**三步同步链**（缺一就有死链）：

```
① 图床删图 + 摘除映射   ← 不摘映射的话，接线脚本会把已删的图重新接回卡里
② 整份重写资源模块      ← 已删项因不在映射里而自然消失
③ 重打包 + 全套回归
```

> 交付前必须实测：把被删图的**图床哈希**逐条拿到成品套件里搜 → 必须**零残留**。
> 不要靠「应该删干净了」，靠搜哈希。

## 六、已知坑清单（通用部分）

| # | 坑 | 对策 |
| :--- | :--- | :--- |
| 1 | 归档脚本每次运行会**重写**输出 → 分批调用会让历史记录被覆盖 | 一次性传全部文件；已丢时从白底备份全量重建 |
| 2 | 转透明后 PNG 元数据被剥离，seed 再也取不回 | 归档必须在转换之前 |
| 3 | 图床历史**无法按提示词检索出角色**（tags 里没有人名） | 文件名必须带角色名：`<角色名>_<≤5字姿势>.png` |
| 4 | 后端状态丢失（`unknown batch_id`） | 以**本地落盘文件**为准 |
| 5 | 计数类判定用文本正则数出假数据 | 一律**真跑一遍代码**再数（实测正则数出「33 键」真值是「25 键」） |
| 6 | 改名/设定变更只改了一处 | 全树扫描旧名，只排除备份与历史快照 |
| 7 | 改完脚本没做语法检查 | 立刻 `python -m py_compile` / `node --check`；实测一个半角引号能让整个生成器跑不起来 |
| 8 | 在后台脚本运行期间编辑该脚本 | 边读边执行会导致循环跑两遍；要改就等它跑完 |
| 9 | 编辑 `replaceString` 类字段超长 | 与平台相关，注意各自上限 |

## 七、成人向题材的额外约定

如果这套流程用于成人向内容，有几条独立的工程约定（**这里只讲原则，不含具体词表**）：

1. **负面词表必须按角色分组分家。**
   用于「防止 A 类角色被画成 B 类」的负面词，挪到 B 类角色身上会把 B 的表现直接压平。
   共用批次时用 **per-task negative** 区分，或干脆拆两个批次。
2. **道具/交互物按场景分级**，并写进生成前断言——
   这和「权重数字」一样，写成散文就一定会漏。实测一处偏差导致 120 张整批返工。
3. **封掉一类词会诱发模型「自己发明替代物」填位**，必须把替代物的负面词一起补上。
4. **不要在通用模板里塞题材专用防御词**（如古风服装防御），
   挪用到现代都市题材会把现代服装全压掉；跨题材混合卡两类都不能加。
5. **底线规则的唯一事实源应该是代码里的一个函数**，而不是散在文档中的描述。
   并且要清楚它的**作用范围**：只作用于正向、只在特定条件下启动、负面永远透传。

## 八、复用这套流程需要什么

**必需**：
- 一个**能批量调用**的文生图后端（支持 seed 固定 + 透明背景或纯色背景）。
  **最好选一个能开本机控制接口的桌面端应用**（见第四节）——没有这层，就只能半自动。
- 一个**能执行 shell 或安装插件的 AI Agent**（第四节的两条接入路线之一）。
- Node.js / Python 3.10+（工具链脚本，无第三方依赖的部分可直接跑）
- 一个本地**人物分割 ONNX 模型**（抠图用；没有的话先只做白底 + 泛洪，接受质量折损）

**建议的仓库结构**：

```
.
├── LICENSE                      # MIT
├── README.md
├── docs/
│   ├── pipeline.md              # 本文件的详细版
│   ├── agent-bridge.md          # 第四节：控制桥协议与适配层
│   └── pitfalls.md              # 坑清单
├── config/
│   └── characters.json          # 角色参数档案（单一事实源）
├── tools/
│   ├── check_conflicts.py       # ✅ 已提供：tag 级冲突检查 + 20 条自测用例
│   ├── build_batch.py           # 待补：档案 → 批次 JSON（五层组装 + 门禁）
│   ├── post_process.py          # 待补：归档 → 抠图 → alpha 清理 → 缩略图
│   └── make_contact_sheet.py    # 待补：拼审图
├── agent/
│   ├── nai_direct.mjs           # 待补：CLI 适配层（任何 Agent 可用）
│   └── plugin/                  # 待补：插件适配层（固定主力 Agent 用）
└── .gitignore                   # 忽略产出图片、模型权重、发现文件、本地配置
```

**本仓库当前状态**：文档 + 冲突检查器已可直接使用；
`build_batch` / `post_process` / `agent` 三部分只给了职责定义，需要按你用的后端自行实现。

**开源的三个必做动作**：
1. **脱敏**：清掉本机绝对路径、账号信息、图床密钥、具体卡的角色设定；
   **控制桥的发现文件（含 token）必须进 `.gitignore`**。
2. **可跑性**：`config/characters.json` 提供一个**虚构示例角色**，让 clone 下来的人能直接跑通；
   控制接口不可用时，适配层要给出**明确的诊断信息**而不是静默失败。
3. **写清依赖边界**：哪些是第三方服务、哪些是模型权重（不要塞进仓库）、哪些需要自己申请授权。

## 九、这套流程真正值钱的地方

不是某一条提示词，是这五件事：

1. **把提示词当数据管**，而不是当字符串拼。
2. **在生成之前把错误挡住**，而不是生成之后靠肉眼捞。
3. **把生图能力变成 Agent 可调用的确定性接口**——换 Agent 零成本，批量才成立。
4. **单一事实源 + 整链重跑**，而不是到处手改产物。
5. **机器只管像素和账目，审美永远归人。**
