# 当前 MMD 通用全局状态前端记录维护方案

配套代码：[`全局状态记录维护.js`](./全局状态记录维护.js)

本文只描述当前 MMD 的前端状态记录方案。状态对象、字段、渲染界面和模型输出协议由使用者定义；本文不提供特殊文本格式范例，也不包含任何具体项目内容。

# 使用说明

## 1. 数据链路

完整链路为：

特殊文本格式 → MMD 正则 → 隐藏 DOM 中间态 → `parseMessage` → reducer → localStorage → `render`

建议先为模型输出设计独立、低冲突的特殊格式，再用 MMD 正则把它转换为隐藏的 light DOM 中间态。中间态必须满足以下条件：

- 使用固定且唯一的选择器，供 `parseMessage` 精确读取。
- 保存在消息的 light DOM 中，不能放进 Shadow DOM。
- 正则只负责结构化和隐藏数据，不负责维护跨轮状态。
- 状态字段发生变化时，同时修改模型输出规则、正则替换结构和 `parseMessage`。
- `parseMessage` 只读取中间态，不读取正文、可见卡片或运行时生成的界面。

当前 MMD 的正则会在 Markdown 处理前运行。隐藏中间态应使用平台允许保留的普通元素，并避免在其他正则源码中写入完整触发标记，防止正则之间相互替换。

## 2. 定义维护规则

接入前必须定义六项内容：

1. `storageKey`：当前状态账本唯一使用的 localStorage 键。
2. `version`：严格版本号；结构变化时递增。
3. `createInitial`：返回全新的空状态。
4. `parseMessage`：把单条消息的隐藏中间态转换为本轮状态片段；没有中间态时返回 `null`。
5. `mergeIncremental`：把最新状态片段合并进已有持久状态。
6. `rebuildHistory`：只根据已加载历史生成完整状态。
7. `render`：根据完整状态刷新界面。

`createInitial`、`mergeIncremental`、`rebuildHistory` 和 `render` 操作的状态类型必须一致。`parseMessage` 必须是纯函数：相同 DOM 得到相同结果，不得在解析结果中写入当前时间、随机值或界面临时状态。

## 3. 装配与启动

先让 `全局状态记录维护.js` 在当前 MMD 的全局界面脚本中执行，再创建管理器。通用装配顺序如下：

```js
const api = window.GlobalStateMaintenance;

const manager = api.createStateManager({
  storageKey,
  version,
  createInitial,
  parseMessage,
  mergeIncremental,
  rebuildHistory,
  render
});

manager.start();
```

`manager.start()` 会先读取 localStorage 并渲染现有状态，再启动回复 poller。界面销毁时调用 `manager.stop()`；手动刷新按钮直接调用 `manager.refreshAll()`。

若状态是按唯一键维护的记录列表，可直接组合内置 reducer：

```js
const mergeIncremental = (current, updates) =>
  api.mergeLatestByKey(current, updates, keyOf);

const rebuildHistory = (messages, parser) =>
  api.rebuildLatestByKey(messages, parser, keyOf);
```

累计型唯一记录将全量 reducer 改为 `rebuildUniqueByKey`。映射、树、分组对象或其他状态结构直接提供自定义 reducer，不需要修改核心库。

## 4. poller 增量更新

`createReplyPoller` 使用当前 MMD 的固定结构：

- 观察根节点：`#msglistview.chat-body`
- AI 回复：`.item.Ai`
- 当前候选：倒数第二个 AI 回复节点
- 稳定标志：存在可见 `.modify-btn`
- 回复正文：`.content.left`
- 防抖时间：1000 毫秒

每次稳定回复可能变化时执行以下流程：

1. `parseMessage` 读取最新回复的隐藏中间态。
2. 返回 `null` 时结束，本地状态不发生变化。
3. 使用 `JSON.stringify` 为解析结果生成内容指纹。
4. 指纹与上次相同时结束，避免平台重复修改 DOM 导致重复写入。
5. `mergeIncremental` 用最新片段计算新状态。
6. localStorage 只写入一次。
7. `render` 使用写入后的完整状态刷新界面。

列表状态使用 `mergeLatestByKey` 时，最新回复中出现的键会替换旧记录；最新回复未出现的键继续保留。因此增量扫描不要求模型每轮重复输出所有历史对象。

## 5. localStorage 持久记录

当前 MMD 的 `window.localStorage` 由聊天页代理且只允许读写白名单 key，自定义状态键必须使用 `CUSTOM_` 前缀；非白名单写入会被静默忽略，读取返回 `null`。

`createLocalStore` 使用固定信封保存状态：

- `version`：调用方指定的严格版本号。
- `updatedAt`：每次写入时生成的时间戳。
- `data`：调用方维护的完整状态。

首次读取且键不存在时，只返回 `createInitial()` 的结果。已存在数据的版本与当前版本不一致时直接抛错，不迁移、不兼容、不尝试读取其他键。

持久层只保存可由消息状态确定的数据。当前页面、弹窗开关、加载提示、按钮状态、定时器和刷新令牌均留在内存中。

修改状态结构时必须同时完成：

1. 递增 `version`。
2. 修改 `createInitial`。
3. 修改解析和 reducer。
4. 明确处理原 localStorage 数据；核心库不会处理旧数据。

## 6. 加载历史与全量重建

`refreshAll()` 使用刷新令牌保证只有最后一次刷新可以落盘。当前 MMD 历史加载使用：

- 滚动容器：第二个 `.uni-scroll-view`
- 加载标志：`.loading-warpper`
- 历史消息：全部 `.content.left`

执行顺序为：

1. 创建新的刷新令牌，使之前的刷新任务失效。
2. 将历史容器滚到顶部并派发 `scroll` 事件。
3. 等待加载标志消失，再等待页面完成本轮插入。
4. 重复上拉，直到滚到顶部后不再出现加载标志。
5. 收集全部已加载消息。
6. `rebuildHistory` 只根据这些消息建立新状态，不读取旧账本参与归并。
7. 检查刷新令牌仍有效。
8. 一次性覆盖 localStorage、调用 `render`，最后回到底部。

`rebuildLatestByKey` 从最新消息向最早消息扫描，同键只保留最新记录；`rebuildUniqueByKey` 按历史顺序扫描，同键只记录一次。其他历史语义由自定义 `rebuildHistory` 明确定义。

调用 `cancelRefresh()` 或 `stop()` 会使正在运行的刷新失效。失效任务不会覆盖 localStorage。

## 7. 给 AI 的函数自定义说明

让 AI 基于本方案制作具体状态模块时，必须遵守以下约束：

1. 只定制存储键、版本号、中间态选择器、`parseMessage`、`keyOf`、两个 reducer 和 `render`。
2. 不修改当前 MMD 的消息、稳定按钮、历史滚动容器和加载标志选择器。
3. `parseMessage` 只读取正则生成的隐藏中间态；不得从可见正文猜测状态。
4. `parseMessage` 没读到中间态时返回 `null`，读到时返回确定性结果。
5. 增量 reducer 只处理最新片段与现有完整状态，不扫描历史 DOM，并保证同一片段重复提交时结果不重复累加。
6. 全量 reducer 完全忽略 localStorage，只以传入的历史消息为数据源。
7. 状态结构改变时同步修改正则、中间态选择器、解析函数、空状态和版本号。
8. `render` 只消费完整状态，不写 localStorage，不反向修改中间态。
9. 不加入备用选择器、旧版本迁移、跨平台分支、字段别名、解析兜底或 `try/catch` 静默恢复。
10. 不把任何具体业务字段写入通用核心库。

# 函数列表

所有函数均由 `window.GlobalStateMaintenance` 暴露。

## `createLocalStore`

```js
createLocalStore({ key, version, createInitial })
```

创建严格版本化的 localStorage 读写器，返回：

```js
{ key, version, read, write }
```

- `read()`：键不存在时返回新空状态；存在时校验版本并返回 `data`。
- `write(data)`：写入版本、更新时间和完整状态，并返回传入的状态。

## `mergeLatestByKey`

```js
mergeLatestByKey(current, updates, keyOf)
```

用于列表型增量更新。`updates` 中出现的键替换 `current` 中的同键记录，未出现的旧记录保留。返回新数组，不修改输入数组。

## `rebuildLatestByKey`

```js
rebuildLatestByKey(messages, parseMessage, keyOf)
```

用于快照型列表的历史重建。从最新消息向最早消息扫描，每个键只保留第一次读到的记录，返回按最新记录优先排列的新数组。

## `rebuildUniqueByKey`

```js
rebuildUniqueByKey(messages, parseMessage, keyOf)
```

用于累计型列表的历史重建。按消息历史顺序扫描，每个键只写入一次，返回按首次出现顺序排列的新数组。

## `createMmdHistoryLoader`

```js
createMmdHistoryLoader()
```

返回当前 MMD 历史加载器：

```js
{ loadAll, scrollTop, scrollBottom }
```

- `loadAll(isCurrent)`：持续加载历史；`isCurrent()` 返回 `false` 时停止。
- `scrollTop()`：触发一次顶部历史加载。
- `scrollBottom()`：滚到当前聊天底部。

## `createReplyPoller`

```js
createReplyPoller({ parseMessage, onUpdate })
```

返回：

```js
{ start, stop, tick, schedule, apply }
```

- `start()`：观察当前 MMD 消息列表并安排首次扫描。
- `stop()`：停止观察并清除待执行扫描。
- `tick()`：立即检查一次最新稳定回复。
- `schedule()`：按固定防抖时间安排扫描。
- `apply(message)`：解析并按指纹提交指定消息，成功返回 `true`，无中间态或指纹未变化时返回 `false`。
- `onUpdate(fragment, message)`：仅在解析结果存在且指纹变化时调用。

## `createStateManager`

```js
createStateManager({
  storageKey,
  version,
  createInitial,
  parseMessage,
  mergeIncremental,
  rebuildHistory,
  render
})
```

组合持久层、poller、历史加载器和 reducer，返回：

```js
{ start, stop, read, applyLatest, refreshAll, cancelRefresh }
```

- `start()`：读取持久状态、渲染并启动 poller。
- `stop()`：停止 poller 并取消历史刷新。
- `read()`：读取当前持久状态。
- `applyLatest(message)`：手动解析并增量提交指定消息；无中间态时返回 `false`。
- `refreshAll()`：加载全部历史并全量重建；成功返回 `true`，被取消返回 `false`。
- `cancelRefresh()`：使当前历史刷新令牌失效。

实际可执行实现以配套 JS 文件为准。该文件可直接进入当前 MMD 全局脚本或构建流程，不依赖本项目其他模块。
