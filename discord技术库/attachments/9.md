# 状态栏简史
## ——MMD 平台上，八个人与一座堡垒

> 这不是胜利者的清单。这是失败者、幸存者、和那个不肯放弃的人的故事。
> 从蛮荒时代到工业交付，八位作者花了不到两年的时间，把一门「在不可能的敌意环境里写前端」的手艺，
> 从一个模模糊糊的念头，一步一步凿成了一座工具箱。
> 每个人登场时，面对的都是前人留下的、没有被解决的最难问题。
> 每个人的方案，后来都被人继承，也被人抛弃，但没有人的贡献真正消失。
> 这不是进化。这是积累。

---

## 序幕 ｜ 蛮荒

你想象这样一个场景。

你写好了一张角色卡。主角是一个落魄的侦探，在赛博朋克的城市里调查失踪案。你给 AI 写了一套精妙的性格设定、一套环环相扣的世界观、一套紧张刺激的开场白。你点击发送。

AI 的回复里有一段状态栏。用 HTML 写的。生命值、魔力值、装备列表、天气。看起来挺像回事的。你挺满意。

然后你玩了 50 轮。

50 轮之后，你看着屏幕上炸成乱码的状态栏，看着被莫名其妙换行的装备列表，看着一个 30 轮前就应该消失的「左臂骨折」标记还在顽固地闪烁。你的 Token 账单已经烧掉了不知道多少。你开始怀疑自己是不是选错了平台。

不是你选错了平台。是**那时的状态栏，根本不应该存在**。

它是一场完美的风暴。五个因素，每一个单独拎出来都不致命，组合在一起就是灾难。

模型每轮都要重写一遍完整的 HTML 状态栏。一个永远不变的装备说明，它重复写了 200 遍。Token 像没有关的水龙头一样流走。这是**烧钱**。

偶尔它漏写了一个 `</div>`。一个标签没闭合，整个页面文档对象模型树崩塌，状态栏变成了一堆裸奔的尖括号和乱码。在足够长的对话里，这不是概率问题。这是**必然**。这是**崩界面**。

HTML 字符串经过平台的 markdown 渲染管线时，被自动补上空 `<p>` 标签，被加上斜体标记，被注入花里胡哨的 font 标签。你写了一段干净的 HTML，屏幕上是带着诡异间距和随机颜色的残骸。这是**被平台揍**。

模型需要从上下文里翻找上一轮的血量，再减去这一轮的伤害值，再减去上上轮的中毒持续伤——它不是一个计算器。它在做角色扮演。让它算数学题是逼它出错。10 轮之内，数值必然漂移。这是**算错数**。

更隐蔽的，是**失忆**。有些信息如果连续几轮没有被提及，就悄悄从模型的注意力窗口中滑出去。50 轮之后，它已经不记得主角还在中毒。你已经放弃纠正它了。

这就是蛮荒。你发了消息，得到了状态栏。然后你发现它正在一点一点地腐烂。

有人第一个说出了那句和所有人相反的话。

他不觉得应该让 AI 写得更好。他提出**不让 AI 写任何 HTML**。

这个人是柑硕。


## 第一章 ｜ 柑硕 —— 那根火柴

当所有人都盯着「怎么让 AI 把 HTML 写得更工整」的时候，柑硕问了一个让所有人沉默的问题：

**「为什么是 AI 在写界面？」**

在正常的前端开发里，设计师画界面，程序员写 JS 逻辑，API 吐 JSON 数据。没有人会要求 JSON 自己把自己渲染成 DOM。但在 2024 年的 MMD 社区，所有人都默认了「AI 应该手写 HTML 状态栏」——这不是因为合理，是因为从来没有人质疑过。

柑硕是第一个质疑的人。

他的方案，在今天回看，优雅得如同数学定理：AI 不再输出 HTML。只输出**被格式化的纯数据**。

```
AI 不再写：
  <div class="hp-bar">【生命值】78/100</div>

AI 只写：
  zy="hp:78/100,mp:45/60"
```

前端 JS 拿到这串数据，自己去查对应哪个 HTML 骨架，自己去填对应的 `<span>` 位置。

省了多少？他测算过：首条消息省 40%，后续更新省 90%。那些一辈子不变的角色名、职业、世界观背景，终于不用每轮重写了。但数据精简只是开胃菜。真正让后来人跪服的是第二件事。

**继承。**

这个思路的源头，来自**心月狐**。他在更早的时候就在整体替换法中注入了 JS，实现了向上回溯——当前消息缺失的字段，引擎会自动向上一条消息查找，填补到 UI 上。柑硕把这颗种子埋进了键值法的土壤里，长出了全新的东西：当前消息只更新了 HP。姓名、职业、金钱——没写。没关系。JS 会自动**向上遍历所有历史消息**，找到最近一次有效值。那条 10 轮之前的完整数据，跨越时间线，回到 UI 上。

```
第 N-3 条消息：nm="勇者" mn="1000" zy="hp:100/100,mp:60/60"
第 N 条消息：   zy="hp:80/100"                             ← 只写了一个字段
屏幕上的结果：  nm="勇者" mn="1000" zy="hp:80/100,mp:60/60"  ← 全回来了
```

他还设计了一套极其紧凑的键名体系。不是 `healthPoints` 和 `currentLocation`，而是 `hp`、`loc`、`nm`。他规定分隔符——`:` 分割名和值，`/` 分割当前和最大，`,` 分割多项，`|` 分割子项。三区独立——环境信息、角色状态、选项列表，各自放进不同的 `data-*` 属性。

对于触发机制，他选择了 `<img onerror="...">`。放一张永远加载不了的图，浏览器在图片失败时会去执行 onerror 里写好的 JS。简陋得近乎粗暴，但在 `<script>` 被禁的平台环境里，这就是唯一的火种。

**柑硕没有被超越。** 他贡献的不是一个方案，是地基。数据与视图分离。「没输出的？从历史里找」。这两条原则后来被每一份方案无条件继承。后人在他的地基上盖了更高的楼，盖出了 Shadow DOM 隔离，盖出了 Web Components 标准化。但地基还是他的。

而且，如果你的角色卡只有五个字段——HP、MP、金钱、地名、天气——柑硕的方案至今仍然是最佳选择。你不需要 13K 的雷达引擎，不需要 Shadow DOM，不需要正则链式拼接。你只需要看 5 分钟，看懂他的 `findData` 函数，就足够了。

一炬之火。后来人只是各自分去，取了火种。

## 第二章 ｜ 澄清 —— 那个用肉身探雷的人

柑硕给出了绝美的数据格式。但他回避了一个更底层的问题：

**代码本身怎么在这种环境里活下来。**

当时的 MMD 平台对注入代码的限制，不是「不推荐」，是「会死」。

你写了一个 `<script>` 标签？服务端直接剥离，一个字都不留。你把 JS 拆成多行方便调试？平台从第一个换行处把后半段全部截掉。你写了一个 `i < length` 做循环判断？HTML 实体转义把 `<` 变成了 `&lt;`，你的循环逻辑炸了。你给一个按钮加了 `id="saveBtn"`？整个对话里所有消息都渲染在同一个 HTML 页面——第二条消息里又出现了一个 `saveBtn`，浏览器崩溃了，所有同类组件全部失效。

这不是技术限制。这是一场**猎杀**。

澄清是第一个不抱怨环境的人。他不是在写代码。他是在**测绘雷区**。他逐个试探每一个角落，找出了哪些路能走、哪些会炸。

`<script>` 被封了？但 `<img src="x" onerror="...">` 还活着。图片加载失败，浏览器会自动执行 onerror 里写的 JS。绕过了。

多行 JS 被截断？那就把所有代码压缩成严格的一行。没有换行给你截。

`<` 被转义？那就不写 `<`。`i != length` 替代 `i < length`。`a == b` 替代 `a === b`。绕过了。

重复 `id` 冲突？再也不给元素加 `id`。用 `class`，用 `data-*`，用时间戳生成唯一后缀。

在绕过所有雷之后，他设计出了一套被后来所有人沿用至今的**标准架构**：

```
AI 输出数据块 → 正则捕获 → 替换成 HTML 模板
  → 隐藏 <p> 标签保存原始数据 → <img onerror> 点火
  → JS 读取隐藏 <p> 的 textContent → 运行时拆分键值对
  → 更新对应 DOM 元素的文字内容
```

每一步都踩在平台的窄缝里。每一步都可能被下一个平台更新封杀。但在那个时间点，**它跑起来了**。而且不只是跑起来——它结构清晰、扩展简单、调试友好。`::` 和 `;;` 做分隔符，`DGS_KV_PANEL_V2_START▶...◀END` 做数据块标记，正则一把抓，一个新字段的加入只需要三步：数据块里加一行、HTML 模板里加一行、JS 里加一行。

这就是 **KV-Robust V2.0**。不是最优雅的方案。但它是那个时代里唯一能活下来的方案。

很长一段时间里，「onerror + 单行」就是 MMD 开发的默认起点。每一个后来的人在写第一行 JS 之前，都会想起黑洞猫画的那张雷区地图。

他是幸存者。然后他让所有人都成了幸存者。

## 第三章 ｜ 黑洞猫 —— 让不该留下的东西死掉

在柑硕和澄清各自奠下地基之后，黑洞猫做了两件只有他才做得到的事。

KV-Robust 让代码在雷区里活下来。但一个 200 轮的跑团跑着跑着，玩家发现了一件诡异的事。

日常的咖啡馆对话，模型开始推演出暴力。温和的牵手突然被描述成带有攻击性的动作。50 轮前的战斗里出现过「左臂骨折」，这个词还在上下文里，像一个钉子一样钉在模型的视野中。它没有变傻。它的注意力被几个高刺激的锚点扯住了。

没有人往上下文里灌过暴力倾向的设定。但历史记录本身就是毒药。

黑洞猫在《混合态雷达法》论文里做了一个洞察。这个洞察的深远程度，让后来影渲法的开发者直接把它原封不动搬了过去：

**不是所有数据都该活一样久。**

他把状态栏的数据分成了五级。主角姓名、世界观纪元——世界是建在这些东西上面的，不能丢。这是**第一类**。生命值、当前地点——每轮都在变，得跟紧。这是**第二类**。暗骰结果、杀意阈值——AI 需要知道但不能让玩家看见。这是**第三类**。

然后他停了一下。写下了**第四类**。

战损评估。极端感官。特殊体液描述。它们有一个共同点：**它们的信息密度极高，高到会绑架模型的注意力。** 50 轮之后，模型还在下意识地围着「肋骨碎裂」这个词打转。这是**上下文污染**。

雷达法的解法残酷到了优雅的地步：第四类数据不继承。战斗结束，模型停止输出战损字段，引擎就**不在 UI 上渲染它**。这条信息从模型的视野里消失，不留痕迹。污染链被物理切断。

他把这种数据叫**液态快照**——用完即焚。和第一、二、五类的**固态底座**相对。双轨生命周期。一套理论，把状态栏从「怎么显示」拖到了「怎么保护模型的长线智商」。

雷达法还有几样只有它才做得到的本事。

**模糊特征嗅探。** 模型自由发散出一个「火焰长剑」，引擎不认识——但它嗅到了「剑」这个特征字，自动把这个未知键名路由到装备区渲染。这意味着写雷达法状态栏的人不需要告诉模型「你必须输出这些精确的键名」。模型可以即兴发挥，引擎会接住它。

**全量历史扫描。** 独立的正则引擎直接检查全部历史气泡的文字内容，不受平台渲染深度限制。不会出现 20 轮后「失忆」。

**虚拟 DOM 劫持对抗。** 平台有时会重绘页面，把外部注入的节点抹掉。雷达引擎在渲染完之后的 2.5 秒内，像雷达一样持续自检。被抹了？从内存缓存里原地重建。5 次之后，停止扫描，释放监听器。整个过程对玩家无感。

除了雷达法这套惊世的理论和引擎，黑洞猫还做了另一件事——他早年端出的**分段式正则替换美化法**，是混合态雷达模块化思想的直接前身。雷达之所以能从"次抛式自毁雷达"一步步走到"全局哨兵"，分段法的那句"一整块东西，拆开"功不可没。而真正触发从次抛到全局的最后一跳的，是一个意外的动力——**迪浦西 v4p 不喜欢生成 `<ztl>` 标记**，每次让它输出锚点都像在逼它做不情愿的事。黑洞猫索性把触发机制彻底翻过来，引擎不再等模型发锚点，自己监听 DOM 变化自动触发。全局哨兵雷达由此诞生。

代价是：引擎本体外加防御补丁，大约 15K 字符。

15K。不是写业务逻辑。是和一个敌意环境谈判。

后来人站在他的肩膀上，用 Shadow DOM 的隔离机制把 15K 缩减到了一行。但这不意味着雷达法应该被取代。隔离的路不通的时候，拉锯战的经验仍然有效。没有黑洞猫，没有人在那个战场上打过仗。

## 第四章 ｜ 澄清 —— 第一个人说「两张地图可以拼在一起」

澄清的角色，在这段历史里有些特殊。

他是键值法的首创者——在柑硕抓取式出来之前，他就把整体替换改成了键值对输出。他也是 KV-Robust 的作者——在柑硕的抓取式之后，他又把抓取式的思想融入键值法，端出了 onerror 点火器、单行压缩、雷区测绘的整套标准架构。

此时社区里并存着两条路：一条是他自己的 KV-Robust——纯文本键值对配合 onerror 引擎；另一条是柑硕的抓取式——HTML 属性式数据配合 DOM 继承。两套都有人用。两套不能合在一起。

如果你想用柑硕的 `zy="hp:78/100,mp:45/60"` 格式，你就得上柑硕的 `data-f` 插槽和 `findData` 继承逻辑。如果你想用 KV-Robust 的 onerror 引擎架构，你就得遵守 `::` 和 `;;` 分隔符规范。大家默认了这是选择题。

澄清是第一个说**「为什么不能都要？」**的人。

他把柑硕的 `data-env`/`data-st`/`data-opt` 三区分法和 DOM 向上继承，原封不动地保留了下来。同时，把触发机制换成更简洁的 `<status>` 标记，装进 onerror 引擎。这件事同时需要精确理解两套体系的每个细节，需要知道哪些能直接对接、哪些需要适配层、哪些会互相冲突。他做到了。

不止于此。他做了第二件对后来影响深远的事情：把状态栏的渲染拆成**三条独立正则**。容器骨架 + CSS 是一条。主 HTML 结构是一条。JS 解析逻辑是一条。再不把所有东西塞进同一条替换规则里。这个「分段」思想的直接继承人：醉猫的链式规则、锐的五类文件架构——本质上都是在澄清打开的那个方向上的延伸。

他还干了一件全社区都应该感谢他的事：他是第一个**系统性地定义编码约束**的人。在 onerror 环境里 `let`/`const` 不能用、箭头函数不能用、`innerHTML` 拼接不能用、`cssText` 赋值不能用——必须 `var`、`function`、`createElement`。后来醉猫用实机测试推翻了其中几条（ES6 其实可以跑），但在那个时间点，这是一份**生存手册**。不遵守的人，代码会炸。遵守的人，至少不会死在语法层面。

还有一件事，小到只有踩过坑的人才会倒吸一口凉气：他发现了 img 标签必须放在容器闭合标签 `</div>` 的内部，否则 `this.closest()` 返回 null——整个 onerror 引擎静默失效，不报错。一个字符的位置之差，决定了一个面板是正常渲染还是完全空白。这件小事被后来每一份规范写进了检查清单。

**澄清贡献的不是新理论。** 他是第一个证明了「融合是可能的」的人。在他之前，两条路之间没有桥梁。在他之后，搭建这座桥变成了技术栈里理所当然的一部分。

## 第五章 ｜ 锐 —— 那个不看数据只看系统的人

锐是所有人里最讲不清楚自己在干什么的一个人。

你问他「你的数据格式是什么」，他会反问你「格式有那么重要吗？」你问他「你的继承策略是什么」，他会说「那是引擎层的决策」。他不是在回避。他是真的不关心。

问他关心什么，他会说——

**「当用户打开页面，所有历史消息的 onerror 一起触发的时候，你怎么知道第 3 条消息的引擎不会在第 10 条之后跑完？」**

整个社区静默了三秒。

这个问题从澄清 KV-Robust 时代就存在了。每条回复都带着自己的状态栏触发 img。页面一打开，几十个 img 的 onerror 近乎同时点火。它们的加载顺序由网络栈决定，不保证和回复的时间顺序一致。如果第 3 条的 onerror 晚于第 10 条触发——旧数据就会覆盖新数据。

**面板错乱。状态倒退。**

澄清踩雷的时候没踩到这个——他不是没遇到，是遇到了但那个阶段还有更紧急的雷要排。柑硕没有这个问题——他的方案里只有一条消息在工作。但一个长对话有 200 条消息的场景里，这不再是可以忽略的边缘情况。这是一个系统级的 bug。

锐伸手，在黑板上写了一行：

```javascript
var replies = document.querySelectorAll('.content.left');
var latestReply = replies[replies.length - 2];
```

用 DOM 节点的位置做裁判。不靠图片加载顺序，不靠时间戳，不靠锁。靠 DOM 顺序。倒数第二个是已完成的最新回复（最后一个是正在生成中的容器）。**最新仲裁**。

然后他在那行代码下面，继续写。

五类文件架构——界面、CSS、初始化代码、回复代码、正则列表。不再把一切塞进同一个大函数。初始化只跑一次。回复代码逐条触发。每个文件不跨界。六步执行链——`固定自身引用 → 等待初始化 → 处理当前数据 → 判定是否最新 → 更新全局视图 → 删除触发节点`。每一步选做，但框架在，后人不再需要每次都从头决定「这段代码应该什么时候跑」。

视图分类——全局单例（侧边栏、地图、弹窗，整个页面只有一个）和回复级重复（每条回复独立的状态栏块、选项块）。两类职责不交叉。

这些概念和具体渲染技术**全部无关**。你用 light DOM 要做，用 Shadow DOM 也要做。Godcount 的 `connectedCallback` 生命周期和影渲法的 per-message 渲染模型——在它们的底层，锐画的六步执行链一直在安静地运转。

**锐提供了元语言。** 后来的所有人，用他的语法说自己的话。

## 第六章 ｜ 醉猫 —— 那个不写理论只跑测试的人

前五个人给出了理论、架构、数据格式、继承策略。醉猫做了一件没有人想做但所有人都需要的事：

**他把五个人的方案放在一起，在真实的 MMD 页面上，一条一条跑。**

理论 MMD 和真实 MMD 之间有缝隙。那些缝隙是平台升级悄悄改变的参数、前人没有覆盖的边缘情况、文档里写着「不能做」但实际上「可以做」的意外。醉猫的 11 万字规范——从 v7 到 v8——本质上不是规范。是**集成测试报告**。

他跑出的东西比任何理论都硬。

前人文档说 replaceString 字符上限是 10000。他跑到截断点——**20000**。含链式标记。前人文档说 ES6 在 onerror 里绝对禁止。他一组语法探针扔进去——`const`、`let`、箭头函数、模板字符串——**全绿**。只是不推荐。前人文档说 `<script>` 标签完全不能用。他发现**允许三种非执行 type**：`application/json`、`text/plain`、`text/json`。

最恐怖的一个发现：`\r` 字符。不是换行 `\n`。是回车 `\r`。当 `\r` 出现在 `<script type="text/plain">` 的代码里时，`eval()` 会**静默失败**。不报错。不警告。代码不跑。你盯着屏幕看了两个小时，你根本不知道问题出在回车符上。零级致命红线——醉猫用一整个通宵锁定了它。

他还发现了 `className` 拼接的暗坑。三元运算符拼接空格——`d.className = 'z-cls' + (flag ? ' on' : '')`——在单行压缩时，空格可能被吃掉。`on` 粘在了 `z-cls` 上。解决方案不是「别用三元」，是**直接用完整字符串赋值**：`d.className = flag ? 'z-cls on' : 'z-cls'`。

他贡献了几个工程创新：**链式规则**——`&继续N&` 标记把多条正则拼接起来，突破了单条的字符上限。**美化与功能分离**——超 20000 字符时拆成两条独立规则，纯视觉调整只改美化层，纯逻辑调整只改功能层。**错误三次触发全面检查**——同一个问题修了三次还没好？停下来。检查 JSON 括号层级、检查 `\r` 字符、检查标记一致性。不要继续在同一个方向打补丁。

**醉猫是拿着秒表和卡尺的那个人。** 他从来不生产让你惊叹的新概念。但他跑过的每条测试，都变成后来者的免死金牌。

## 第七章 ｜ 影渲法 ShadowCast —— 换了个战场

到醉猫为止，七个作者，所有方案，都在做同一件事：

**在平台现有页面的 light DOM 里注入组件，然后用补丁对抗平台的干扰。**

雷达法的引擎附带大约 15K 的防御代码。MutationObserver 哨兵持续监控 DOM，平台强插一个 font 标签就剥离一个。引号修复函数修正被 CSP 篡改的字符串。三条独立的 CSS 规则压制 markdown 空白条——`p:empty{display:none}` 处理空段落，`p{margin:0}` 兜底误包段落，`br{display:none}` 覆盖单换行。还有染色剥离、信标转换器、全半角兼容正则……**

15K。不是业务逻辑。是**战争开销**。

然后有一个人走出来了。他没有提供更好的补丁。

**洛璃**曾把 Shadow DOM 技术推荐给黑洞猫用来解决全局哨兵雷达的性能瓶颈。随后，他独立提出了一个方案——

> **「不打补丁了。用 Shadow DOM 把整个组件隔离出去。」**

Shadow DOM 是浏览器原生的隔离机制。当组件被渲染在 shadow root 里——内部的 CSS 不会漏出去，外部的 CSS 进不来。**不经过** markdown 渲染管线，免疫空白条。**不经过**平台染色器，免疫 font 注入。类名随便起，不需要前缀防冲突。

雷达法需要 15K 防御补丁才能争取到的东西，影渲法用一行代码包揽了：

```javascript
box.attachShadow({mode: 'open'});
```

这不是「更好的补丁」。这是**换了一个战场**。花了两年的时间在敌意环境里和平台互殴，然后有一个人指着旁边一座山头说「那边不用打架」。

这个人是洛璃。这套方案就是**影渲法**。

影渲法的工程哲学也变了。走进 Shadow DOM 路线的那一刻起，它变成了 **schema 驱动**——字段必须预定义，构建期断言保证键名在引擎配置、数据协议、测试数据三处完全一致。开发者定义 `FIELDS`、跑生成器、产出 json、导入 MMD。不再需要调试 markdown 的神秘副作用。**写好就忘。**

但影渲法付出了一个代价，一个它永远无法追回的代价：Shadow 边界同时屏蔽了跨气泡历史扫描的能力。雷达法那个让引擎自动嗅探「火焰长剑」并归位到装备区的模糊路由——在 Shadow DOM 隔离下**做不到**。

这不是 bug。这是隔离的本体论代价。你选择不与平台对抗，就必须接受更严格的结构约束。

初版影渲法还有一个隐蔽的缺陷：如果浏览器或运行环境禁用了 `attachShadow`，整个面板会**静默消失**。不是被平台打掉——是自己没能扛住自己的技术前提。ShadowCast 2.0 修复了这一点：引擎会先尝试 attachShadow，失败则自动回退到 light DOM 渲染，面板照常显示，只是少了隔离层。

2.0 还吸收了哨兵雷达法实测中的几个硬核优化：跨气泡缓存的单张 `CSSStyleSheet`（N 条消息不再创建 N 份相同样式）、事务式渲染（内存里建完整再一步挂载，异常时回退，不留破碎 UI）、key 同义词归一化（模型写 `HP` 和写 `hp` 都归到同一个标准键名下）。

**影渲法的贡献是范式转换。** 在它之前，全社区的默认选择是「在 light DOM 里打补丁」。在它之后，有一半的新项目选了另一条路，一条不需要打仗的路。

## 第八章 ｜ Godcount —— 铁律的掘墓人

从 KV-Robust 时代算起，六位作者，三年时间，所有的方案都共享同一个假设：

> **「`<script>` 不能用。必须用 `<img onerror>` 点火。」**

这条铁律支撑了整个社区的基础设施。onerror 点火器、单行压缩、`data-s` 存多行、`eval` 触发——一整套绕过技术，都建立在这条线上。

然后平台更新了。`<script>` 被解禁了。

没人注意到。

不——有人注意到了。但没有人知道**这意味着什么**。六个月的时间里，人们继续写 onerror 引擎，继续单行压缩，继续把复杂逻辑塞进 `data-s` 然后用 `eval` 引爆。铁律一旦内化，它就不再只是外部环境的限制——它变成了你自己做决策时的默认心智模型。

Godcount 是第一个打破了这种惯性的人。

他重新看了一遍平台现状：`<script>` 解禁了。`document.currentScript` 虽然还是不能用（所以不能 per-message 自定位），但全局 `<script>` 完全足够做一件事——**注册一次 Web Component 类，然后让浏览器接管所有后续的逐条实例化。**

```
被铁律束缚的认知：
  每条消息带一份 img onerror → 一份完整的引擎副本
  10 条消息 = 10 份相同的 JS，重复加载、重复解析

铁律失效之后：
  全局放一次 <script>，注册 class ZLiveWidget extends HTMLElement
  每条消息只需要一个 <z-live-widget></z-live-widget> 自定义标签
  浏览器自动调用 connectedCallback() → 自动 attachShadow → 自动渲染
  10 条消息 = 1 份类定义 + 10 个浏览器原生调度的生命周期
```

代码量骤降。事件绑定回归标准的 `addEventListener`，不再需要 `data-s` 存代码然后 `eval` 掏出来。从「在敌意环境里匍匐前进」到「正常写前端」，中间只隔了一层 Web Components 标准。

他拆出了三段正则来承载这个架构：数据隐藏层——`[#键名=键值#]` 被信标转换器包进隐藏 `<span class="z-live-data">`，和雷达法的信标思路一脉相承但边界更明确。UI 触发层——`<GC_UI>` 被替换为 `<z-live-widget>` 自定义标签。全局引擎层——`<GC_SCRIPT>` 注入在功能栏，类定义只注入一次。注意第三段正则不在每轮对话里——这恰好是 `<script>` 全局注册架构的核心优势。

他还补上了一个影渲法没有单独强调、但对两个方案同样致命的陷阱：**Shadow DOM 不能阻止 CSS 可继承属性穿透边界。** `color`、`font-family` 会从宿主页面的白色文字漏进 shadow，让你白底白字什么都看不到。必须显式在 shadow 内部根容器声明 `color: #1c1c1e;`。这不是平台 bug，是 Web 标准的正常行为。太容易踩，太容易忽略。

他内置的工程实践：防重复注册、定时器生命周期管理、根据好感度动态切主题、shadow 内按钮跨边界写回平台 textarea、移动端自动关闭毛玻璃和动画。

**Godcount 不是「影渲法的升级版」。** 影渲法靠 onerror 点火，兼容旧版 MMD。Godcount 靠 `<script>` 全局注册，需要新版平台。他们共享 Shadow DOM 的隔离优势，但在触发机制上分道扬镳——onerror 是封锁期的生存策略，Web Components 是开放后的标准路线。

两个时代，两种答案。

他扔掉了第一根火把——那个在黑暗里撑了无数个夜晚的 onerror 点火器。不是因为那根火把不好。是因为**天终于亮了。**

## 横切 ｜ 工具箱

八个人，每个人都解决了一个只在那个时间点才能被解决的问题。

柑硕的问题：数据格式。澄清 KV 的问题：代码能不能活。黑洞猫雷达的问题：长线之后模型会不会傻。澄清的问题：不同的路能不能合并。锐的问题：系统怎么组织。醉猫的回答：别猜，实测。影渲法的回答：换个战场。Godcount 的回答：铁律不是永恒的。

| 如果你想…… | 找这个人 |
|------------|---------|
| 只有 5 个固定字段，追求最简 | **柑硕**——代码最短，五分钟看懂全部逻辑 |
| 模型自由发散新键名（自创装备/技能/NPC） | **雷达法**——模糊特征嗅探，影渲法和 Godcount 做不到 |
| 追求隔离省心，不想和平台对抗 | **影渲法** 或 **Godcount**——Shadow DOM 一劳永逸 |
| 追求标准前端开发体验 | **Godcount**——Web Components 原生生命周期 |
| 兼容旧版 MMD（`<script>` 仍禁用） | **影渲法**——onerror 全版本兼容 |
| 跨回复全局 UI（地图、侧边栏、弹窗） | **AGENT 架构**——五文件六步链，与渲染技术无关 |
| 快速原型，极简面板 | **KV V4.0 或原生 $field**——零 JS |
| 全局美化（改平台原生元素样式） | **传统穿透方案**——Shadow DOM 隔离和穿透互斥 |

```
柑硕                    —— 数据和视图，从此不再是一家
  ↓
澄清 KV-Robust         —— 在雷区里，一寸一寸试出来的生路
  ↓

  ↓

  ↓
醉猫                   —— 用秒表和卡尺，测出了真实的边界
  ↓
洛璃 影渲法 ShadowCast —— 「不打补丁了。隔离。」
  ↓
Godcount               —— 「点火器。也可以不用了。」
```

**这不是一条进化链。**

每一步都在前人的地基上增加新的能力。但没有人因此过时。柑硕的五字段面板仍然是最简解。雷达法的模糊嗅探仍然是唯一能处理自由键名的方案。锐的最新仲裁仍然是任何复杂注入都绕不开的工程问题。

你需要的时候，不是选「最新的那个」。

是选「最匹配的那个」。
